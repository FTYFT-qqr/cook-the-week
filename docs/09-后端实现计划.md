1. **`migrate.ensure_schema()` 会认老库**：P0-2/P0-5 期间用 `create_all()` 建的库没有 `alembic_version`，

3. **迁移等价性由测试守住**：`tests/test_migrations.py` 把 `upgrade head` 建出的 schema 与
   `Base.metadata.create_all` 建出的 schema **逐表/逐列/索引/外键**比对，ORM 一改而迁移没跟上就会红。
4. **顺手修掉一个假失败**：本机沙箱下 `tempfile.mkdtemp` 的 `0o700` 目录建完就不可访问，

## P1 进度：P1-1 / P1-2 完成（2026-09-11）

**做了什么**

- `recipe_planner/infra/logging.py`：一行一条 JSON 日志，`request_id` 用 contextvar 自动带上；
  stdout + `logs/app.log`（按天轮转留 14 天）。
- `recipe_planner/api/middleware/`：`RequestID`（含对外来 ID 的清洗，防头注入）、`AccessLog`

- `recipe_planner/api/errors.py`：领域异常 → `application/problem+json`
  `{code,message,request_id,status,details.next_steps}`；`message` 一律人话，500 只记日志不回显堆栈。
- `recipe_planner/api/routes/`：健康检查（`/health` 不碰依赖、`/ready` 逐项报告）、菜谱、方案、今晚、档案。
- `recipe_planner/tonight.py`（**新**）：「今晚」状态①–⑤ 的判定与文案抽成纯函数，
  `today/now` 可注入；界面与 API 共用同一套语义。
- `recipe_planner/storage/async_adapters.py`（**新**）：服务端按 `STORAGE` 分派的 **async** 数据入口。
  路由里**不能**用同步门面（`store/profile/db` 末尾那套会往事件循环里再塞协程）。
- `engine.request_scope()`：请求级会话登记；`session_scope()` 检测到就复用 → 一次请求一个事务。

**两个真问题（值得记住）**

1. **异常处理器在 Session 中间件内层**：Starlette 把注册的异常处理器放在中间件栈最里面，
   路由抛出的领域异常会被就地转成 4xx/5xx 响应，Session 中间件**看不到异常** →
   如果只按"有没有抛异常"决定回滚，"出错的请求"照样会被提交。
   现在规则是：**响应码 ≥ 400 一律回滚**（`tests/api/test_middleware.py` 有专门的用例守着）。
2. **`profile_signature` 的算法原来在 JSON / DB 两处各写了一遍**，抽成 `profile_signature_of(p)`
   纯函数，两边都调它（改一处漏一处是迟早的事）。

**验证**：`pytest tests` 60 项全绿（原 13 + 中间件 15 + 只读路由 22 + 今晚状态机 10）；
`self_check` 163/161、`smoke_app` 165/161、`verify_migration` 18 全绿；
`uvicorn recipe_planner.api.main:app` 起服务后，用真实 `data/app.db` 请求
`/health /ready /api/v1/plans /api/v1/plans/current /api/v1/profile` 全部 200，
`/plans/current` 返回 `手撕包菜、麻婆豆腐 / 约 32 分钟 · 预计 ¥14 · 18:30 开始做，约 19:02 能吃上`。

**已知的临时重复**：`app.py:render_tonight()` 里还有一份状态判定，与 `tonight.py` 暂时并存。
P1-7 界面切到 API 后删掉 `app.py` 那份（到时候只留服务端一份，两处文案不会再漂）。

**下一步（P1-3）**：写入路由（`PATCH /plans/{id}/days/{day}`、反馈、省钱、评分、勾选、档案增删），

## P1 进度：P1-3 完成（2026-09-11）

**新增 `recipe_planner/actions.py` —— 单点改动的唯一实现处**

docs/08 §5 要求"成功/失败/空/加载四类状态的措辞由后端产出，前端只负责展示与点击"，
所以"改了什么、没动什么"的句子必须和改动本身放在一起、且只有一份。这个模块就是那一份：
界面（P1-7 切到 API 后）与 API 都调它，不再各写一遍文案。

每个操作返回 `ActionOutcome{kind, message, days, profile, extra, undo, next_steps}`，守住三条：

| 约束 | 做法 |
|---|---|
| **单点**（05 §4 R1） | 每个函数只动它自己那一天的菜（或档案里的一条），其余天原样返回 |
| **回执**（05 §5.3） | `message` 用「已<做了什么>，<哪里没动>」句式，几天没动要写清数字 |
| **可撤销** | `undo` 给**精确逆操作**：换菜用 `replace_day` 还原原来的菜，而不是"再换一次"（再换不一定换回原来那道） |

**接口**（都在 `/api/v1`）

| 方法 | 路径 | 说明 |
|---|---|---|
| PATCH | `/plans/{id}/days/{day}` | `op` = `skip` / `restore` / `people`（当天总人数，绝对值）/ `faster` / `swap` / `replace_day`（撤销用）/ `done` |
| POST | `/plans/{id}/dishes/{day}/{recipe_id}/feedback` | `like` / `dislike` / `lock` / `unlock` |
| POST | `/plans/{id}/save-money` | 挑最贵的一道换便宜的，返回省了多少 |
| POST | `/plans/{id}/rate` | `{day, score}`（2 好吃 / 1 一般 / 0 下次不做） |
| GET·PUT | `/plans/{id}/shopping/checks` | 幂等，全量覆盖 |
| GET·PUT | `/profile` · POST `/profile/clear?confirm=true` · GET `/profile/export` | 档案增删与导出 |

统一回执 `{kind, message, data, action_log_id, undo_hint, next_steps}`；写接口在返回前
`await session.commit()`，并往 `action_log` 记一条（谁在什么时候把什么改了）。

**新增/改动**：`actions.py`（新）、`api/routes/plan_mutations.py`（新）、`api/routes/profile.py`（读写合一）、
`api/schemas.py`（`MutationOut` 等 DTO）、`api/errors.py`（`ActionError` → problem+json）、
`storage/async_adapters.py`（写入分派）、`profile.apply_rating_to_dict`（打分规则原来在 JSON/DB 两处重复）。

**测试**（`tests/api/test_plan_mutations.py`，25 项）：
R1 用**数据库快照前后对比**证明（改了第 2 天 → 只有第 2 天的行变了；改 A 方案不碰 B 方案）；
`undo_hint` 原样再发一次必须回到改动前；回执用正则卡句式；409 场景必须带 `next_steps`。

**验证**：`pytest tests` **85 项**全绿；`self_check` 163/161、`smoke_app` 165/161、`verify_migration` 18 全绿。
真机（真实 `data/app.db`）：幂等 PUT 勾选返回 `已记下买到 0/21 样。` + `action_log_id=1`，提交前后数据一致；
不存在的方案 → `404 plan_not_found 没找到这份方案，可能已经被删掉了。next_steps:[看看还有哪些方案]`。

### ⚠️ 待产品负责人定夺（P1-3 暴露出来的语义不一致）

**"喜欢"是切换，"打分"是确保 —— 建议统一成"确保"。**

- `POST .../feedback {op:like}`：对**已经喜欢**的菜再点一次，会把它**取消喜欢**（toggle，`apply_feedback_to_dict(toggle=True)`）；
- `POST .../rate {score:2}`：对已经喜欢的菜打「好吃」，会**保持喜欢**（`apply_feedback_to_dict(toggle=False)`）。

现状已被 `test_like_on_already_liked_dish_toggles_off` 钉住（不是 bug 没人管，是有人改了会红）。
界面上的「喜欢/不喜欢」是成对按钮，toggle 说得通；但按钮只有「喜欢」一个时，连点两次把偏好清掉会让人困惑。
**推荐**：反馈也改成"确保"（`toggle=False`），另给一个显式的「取消」入口。定了我再改，改完顺带更新 05 §M3。
