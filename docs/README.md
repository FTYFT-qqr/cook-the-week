## 怎么读（按你的目的选）

**要动手改界面 / 写页面**
→ 先读 **05**（有哪些功能、页面怎么分、交互怎么走）→ 再按 **06** 取值（颜色字号间距，不要另起一套）→ 需要依据时回查 04。

**要动后端 / 数据库 / 服务化**
→ 读 **08**（选型、中间件顺序、API 路由、P0–P3 路线与验收；表清单是设计快照）→ 再读 **09**（做到哪一步了、每步怎么验）→ 再读 **07** §1.5「数据在哪」+ §2 代码结构与 §6 踩坑 → 落地时遵守 08 §7 的"同名适配层"约定（界面与现有测试不改）。
→ **但先看 `11` §4.4**：P2（Postgres / Redis / 可观测）目前建议暂停。

**想快速了解这个产品**
→ 读 **01**（是什么、给谁、做到哪）→ 再读 **05** 的 §1 功能地图与 §2 页面结构。

**想知道"为什么界面是这样改的"**
→ **02**（功能闭环 → 为什么加清单打勾/持久化/放宽条件）→ **03**（视觉诊断 → 为什么收颜色、去 emoji）→ **04**（像素证据 → 为什么锁浅色主题、去掉 Deploy）。

**要验收**
→ **13**（当前基线、人工闭环与统一出口）→ **05** §8 体验验收清单（8 条）+ **06** §8 界面自查清单（10 条）。

**想知道"还剩什么没做 / 下一步做什么"**
→ 先读 **13** §3（A/B/C 未完成项登记册）与 §4（交付收尾顺序）→ 再读 **14**（推荐质量、轮换、
结构策略、家庭成员与外部内容的分阶段方案）。

**要做体检 / 复盘投入产出 / 决定下一步做什么**
→ 读 **11**：实测证据（附录 A）、P0 正确性 6 条、P1 一致性 8 条、风险登记册、建议暂停项。

**要对照"理想功能"看实现到哪了 / 定下一版范围**
→ 读 **12**：逐模块完成度、三类差距（A 理想有未做 / B 实现了但基线没有 / C 做了但是坏的）、四批改进方案，以及可直接用作下一版 `05` 范围的表。

## 维护约定

1. **06 是样式的唯一来源**：任何新页面都必须从 `06` 取色板、字号、间距、组件规格，不得另起一套。
2. **05 是功能与流程的基线**：功能增删、页面结构变化，先改 `05` 再动实现；`05` 与 `06` 冲突时，**流程以 05 为准、取值以 06 为准**。
3. **新增文档按编号追加**（下一个空号是 `15-…`），不要插队改号；评审类文档只增不改，结论变化写进新的设计文档。
4. **08 是后端基线**：数据库表、中间件、API 路由的改动先改 `08` 再动实现；数据层改造必须保持 `07` §4 的接口签名。
5. **测试/进度数字只留一处**：对外口径统一为「pytest + `self_check` + `smoke_app` + `smoke_api_app`」，具体数字以实测输出为准，不在多份文档里各写一份（这是 `11` P1-7/P1-8 的教训）。
