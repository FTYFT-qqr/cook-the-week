**两个真问题（值得记住）**

1. **异常处理器在 Session 中间件内层**：Starlette 把注册的异常处理器放在中间件栈最里面，
   路由抛出的领域异常会被就地转成 4xx/5xx 响应，Session 中间件**看不到异常** →
   如果只按"有没有抛异常"决定回滚，"出错的请求"照样会被提交。
   现在规则是：**响应码 ≥ 400 一律回滚**（`tests/api/test_middleware.py` 有专门的用例守着）。
2. **`profile_signature` 的算法原来在 JSON / DB 两处各写了一遍**，抽成 `profile_signature_of(p)`
   纯函数，两边都调它（改一处漏一处是迟早的事）。

## P1 进度：P1-3 完成（2026-09-11）

**新增 `recipe_planner/actions.py` —— 单点改动的唯一实现处**

docs/08 §5 要求"成功/失败/空/加载四类状态的措辞由后端产出，前端只负责展示与点击"，
所以"改了什么、没动什么"的句子必须和改动本身放在一起、且只有一份。这个模块就是那一份：
界面（P1-7 切到 API 后）与 API 都调它，不再各写一遍文案。

每个操作返回 `ActionOutcome{kind, message, days, profile, extra, undo, next_steps}`，守住三条：

| 约束 | 做法 |
|---|---|
| **单点**（05 §4 R1） | 每个函数只动它自己那一天的菜（或档案里的一条），其余天原样返回 |
| **回执**（05 §5.3） | `message` 用「已<做了什么>，<哪里没动>」句式，几天没动要写清数字 |
| **可撤销** | `undo` 给**精确逆操作**：换菜用 `replace_day` 还原原来的菜，而不是"再换一次"（再换不一定换回原来那道） |

**接口**（都在 `/api/v1`）

| 方法 | 路径 | 说明 |
|---|---|---|
| PATCH | `/plans/{id}/days/{day}` | `op` = `skip` / `restore` / `people`（当天总人数，绝对值）/ `faster` / `swap` / `replace_day`（撤销用）/ `done` |
| POST | `/plans/{id}/dishes/{day}/{recipe_id}/feedback` | `like` / `dislike` / `lock` / `unlock` |
| POST | `/plans/{id}/save-money` | 挑最贵的一道换便宜的，返回省了多少 |
| POST | `/plans/{id}/rate` | `{day, score}`（2 好吃 / 1 一般 / 0 下次不做） |
| GET·PUT | `/plans/{id}/shopping/checks` | 幂等，全量覆盖 |
| GET·PUT | `/profile` · POST `/profile/clear?confirm=true` · GET `/profile/export` | 档案增删与导出 |

统一回执 `{kind, message, data, action_log_id, undo_hint, next_steps}`；写接口在返回前
`await session.commit()`，并往 `action_log` 记一条（谁在什么时候把什么改了）。

**新增/改动**：`actions.py`（新）、`api/routes/plan_mutations.py`（新）、`api/routes/profile.py`（读写合一）、
`api/schemas.py`（`MutationOut` 等 DTO）、`api/errors.py`（`ActionError` → problem+json）、
`storage/async_adapters.py`（写入分派）、`profile.apply_rating_to_dict`（打分规则原来在 JSON/DB 两处重复）。

## P1 进度：P1-4 完成（2026-09-13）

**中间件 3/4/5 落地**，栈顺序（外→内）：
`RequestID → AccessLog → Auth → RateLimit → Idempotency → Session → 路由`。
顺序不是随便排的：Auth 在 RateLimit 外层（限流要按 API Key 分桶）、
Idempotency 在 Session 外层（它自己的记录要用**独立事务**提交，不能被业务回滚带走）、
AccessLog 在最外层附近（被认证/限流拦掉的请求也要留痕）。

| 中间件 | 关键行为 |
|---|---|
| **Auth**（3） | `AUTH_MODE=off`（默认本机）放行；`apikey` 时校验 `X-API-Key`（`secrets.compare_digest`）。**apikey 但没配 `API_KEY` → 一律 503**，宁可不可用也不能"以为开了认证其实没开"；`/health`·`/ready`·`/docs`·`/openapi.json` 免认证 |
| **RateLimit**（4） | 令牌桶：普通 60/分钟、`POST /api/v1/plans` 6/分钟（各自独立的桶）；超限 429 + `Retry-After` + problem+json（含 `details.retry_after_sec`）；探针不限流；按 API Key 分桶、无 Key 按 IP；`RATE_LIMIT=off` 可整体关 |
| **Idempotency**（5） | 只对 `POST` + `Idempotency-Key`：成功存 24h，回放时加 `Idempotent-Replay: true`；进行中 → 409 `in_progress` + `Retry-After`；同 key 不同请求体 → 409 `idempotency_key_reused`；**失败不缓存**（否则永远卡在同一个错误）；`text/event-stream` 不缓存（给 P1-6 留好口子） |

**三个实现细节（都踩过）**

1. **幂等 key 必须带端点**：`idempotency_key` 表主键只有 `key` 一列，所以存进去的是
   `sha256(端点 + 客户端 key)` 前 40 位；否则同一个 key 用在两个接口上会互相回放。
2. **只缓存 2xx**：把失败也缓存起来，用户会永远卡在同一个错误上。
3. **`/ready` 增加 `auth` 检查**：认证配错必须在就绪探针里看得见。

## P1 进度：P1-5 完成（2026-09-13）

**为什么做成任务**：一次排菜要调模型 + 校验修正，几秒到几十秒。同步请求会把连接吊住，
客户端刷新一下就不知道到底排没排 —— "我到底敢不敢点"就是这个问题。现在：立刻 202 + `job_id`，
状态写进 `job` 表，客户端轮询（P1-6 换 SSE 推送）。

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/v1/plans` | **202 + `job_id`**（要 `Idempotency-Key` 才幂等；6/分钟限流） |
| GET | `/api/v1/jobs/{id}` | 任务状态（`status/stage/progress/plan_id/error_code/message/next_steps`） |
| GET | `/api/v1/jobs` | 最近任务（排障用） |
| POST | `/api/v1/jobs/{id}/cancel` | 取消（排队中立刻取消；运行中在下一个节点停） |

**状态机**：`queued → running(stage, progress) → succeeded | failed | cancelled`
（超时 → `failed(timeout)`；流水线抛错 → `failed(error)`；没有结果 → `failed(empty)`）。

**`InProcessRunner`**：一个常驻工作线程 + 待办队列，默认并发 1 —— 这自然带来 docs/08 §6 要的
"同一 household 的 plan_week 任务多余入队"，202 里还会回 `queue_position`（"前面还有 1 个任务"）。

**两件如实说明的事**

1. **取消与超时是"协作式"的**：Python 杀不掉线程，所以在每个流水线节点之间检查（外加一次 LLM 调用
   内部的等待只能等它自己返回）。节点粒度是秒级，够用；
2. **任务状态在 `job` 表里**，进程重启后虽然任务没了，但状态查得到（不会出现"幽灵 running"）；
   P2 的 `QueueRunner`（Redis）会补上"重启后 queued 任务可续跑"。

**踩到并修掉的三个真问题**

1. **跨事件循环用连接池会炸**：任务在后台线程里跑，通过 `sync_bridge` 用**自己的事件循环**写库；
   而连接池会把在一个循环里建的连接复用给另一个循环（"attached to a different loop"）。
   文件型 SQLite 改成 `NullPool`（用完即关）——单机家庭场景没有连接开销问题。
2. **`shutdown()` 用哨兵停线程会留"地雷"**：哨兵留在队列里，runner 复用时会立刻把新建的工作线程弄死。
   改成 `get(timeout=0.2)` 轮询 + `_ensure_started()` 清 `_stopping`，现在 shutdown 之后还能再用。
3. **忌口写错会被静默放过**：`allergens` 里出现不在 `ALLERGENS` 里的词（例如"花生酱"），
   过滤逻辑根本不认识它 → **忌口形同虚设**。现在 422 明确拒绝并列出可选项（05 §4：忌口永不妥协）。

**新增/改动**：`api/worker.py`（新，含 `dump_error/load_error`）、`api/routes/jobs.py`（新）、
`storage/repositories.py::JobRepo`（新）、`storage/async_adapters.py::MemoryJobRepo + save_plan + job_repo()`、
`api/schemas.py`（`PlanCreateIn/JobAcceptedOut/JobOut`）、`progress.py`（无 emoji 的 `STAGE_LABELS/STAGE_PROGRESS`）、
`storage/engine.py`（SQLite `NullPool`）、`infra/settings.py`（`JOB_TIMEOUT_SEC`）。

**验证**：`pytest tests` **130 项**全绿；`self_check` 163/161、`smoke_app` 165/161、`verify_migration` 18 全绿。

**SSE 的三条实现取舍**（都写进了代码注释）

1. **先查一次任务再开流**：任务不存在就正常返回 404 problem+json，而不是开一条永远没消息的连接；

**三个设计取舍**（代码注释里有同样的话）

1. **同步客户端**而不是 async：Streamlit 脚本本身是同步的，改成 async 会把重跑、`session_state`、按钮回调全搅一遍；
2. **一次 rerun 一次缓存**：`begin_rerun()` 在脚本开头清缓存，**不猜 TTL**（TTL 要么短到没用、要么长到读到脏数据）；
   任何写入都立刻让整个缓存失效，所以"写完再读"绝不会读到旧值；
3. **不重复领域规则**：档案那半边只实现 `load_profile` / `save_profile` 两个 IO 边界，
   `set_feedback` / `rate` / `liked_names` 全部复用 `profile.py` 里的纯函数 —— 和 `storage/db_profile.py` 一模一样。

### ⚠️ `update_result` 是一座**桥**，P1-8 应该拆掉它

界面原来是自己算好整周、再整份存回去。服务化之后这样不行：清单、花费、忌口冲突、下锅顺序
都是服务端重算的。所以 `client.update_result` 的做法是：**逐天比对、只对真的变了的那天发一个已有的单点操作**
（`skip` / `restore` / `replace_day` / `people`），然后重新读服务端那一份返回。

比对是**事实判断**（哪几道菜不一样、人数一不一样），不是规则判断 —— 规则仍然只在服务端，所以它不是"又一份实现"。
但它确实是个过渡物：**P1-8 应该把界面那 9 处"自己算 + 存回去"**（换一道 / 回家晚了 / 来客人了 / 去掉一道 / 撤销 / …）
**改成直接调服务端的意图接口**（`actions.py` 那一套），桥就能拆掉。那时界面的回执文案也能统一用服务端返回的
`message`（现在还是界面自己拼，两种模式一致，但没有真正合一）。
