## 0. 一句话结论

**这个项目的工程能力，已经远远超出"自己+家人用一个 demo"所需要的水平；而真正卡住它的东西，一件都还没解决。**

| 维度 | 现状 | 判断 |
|---|---|---|
| 技术深度 | FastAPI 服务层（认证 / 限流 / 幂等 / SSE / 任务状态机）、SQLAlchemy + Alembic（16 张表）、5 套可切换的存储后端 | **超出目标一个数量级** |
| 工程纪律 | 270 条 pytest + 3 个回归脚本、AST 源码守卫、迁移等价校验、**33 条踩坑文档化**、里程碑标签 | **个人项目里罕见的好** |
| 正确性 | 实测发现**会静默写坏用户数据**的路径（撤销、完成标记）、**会读不到**的路径（DB 模式的评分）、**提交后回滚**导致"报错但已生效" | **有真实缺陷，且都在用户数据路径上** |
| 质量口径 | 文档自称多套数字（116/110、163/165、270），实测**一次全量运行有 1 条失败**、重跑又全过 | **"全绿"这个验收口径不可靠** |
| 产品 | 菜谱 **38 道**（30 正餐 + 8 早餐），要排「早/午/晚 × 7 天」最多 21 顿；导航 5 页 | **内容供给跟不上维度扩张** |
| 文档 | 11 份文档，交接写得极好；但页面名、导航项数、测试数字、状态字段**四份副本互相矛盾** | **漂移已成事实，不是我一个人看不懂** |
| 管理 | 3 个决策项悬空在 `09` 里等"产品负责人"点头（其中一个是数据语义冲突） | **决策积压正在变成技术债** |

**一句话**：**不是做得不好，是顺序不对。** 在"设计要求还没定稿、内容供给没跟上、三个决策没拍板、数据一致性还有洞"的时候，先把最不影响用户体验的后端生产化设施建完了。

## 2. 用户视角（自己 + 家人真实使用）

我把这一版**当成真的要用一周**去过了一遍：周日排一次 → 每天傍晚看一眼 → 买菜打勾 → 偶尔改一处 → 下周复用。

### 2.1 我确实感受到的进步

- **「今天」页真的懂日期了**：打开就说"今晚 · 第 N 天"，今天那行高亮、已过的日子变淡。
- **多餐能用了**：早/午/晚可勾选，一天三顿各自一张卡、各自的"做完了"，没串。
- **清单能到菜市场**：打勾、已买下沉、导出 CSV / 文本 / A4 单页。
- **改一处不会毁掉整周**：换一道 / 回家晚了 / 来客人了，都只动点名那一处（`test_plan_mutations.py:71-81` 用全库快照守着这一点）。
- **出错会说人话**：还有"可以点的下一步"，不是一句"候选已用完"。

### 2.3 作为用户，我最想要的 3 件事

1. **先把"做过了 / 撤销 / 评分"这三条弄对。** 它们不影响我吃饭，但它们决定**我信不信它**——一旦我发现"撤销"把饭弄没了、状态是假的，我就不会再认真用它。
2. **菜多起来。** 不是要 200 道，而是"21 顿不重样"这个下限要够用；否则多餐反而让重复更明显。
3. **界面别再让我选。** 5 个导航项、两个"排一周"入口、还有一个 DB/JSON 模式差异——家人不需要知道"存储后端"是什么。

## 3. 项目经理视角

### 3.1 范围：最大的问题在这里

**项目自己写的目标**（`01` / `05`）：

> 自己 + 家人真实使用 ｜ demo 阶段 ｜ **不做账号、不做云端同步、不做正式部署** ｜ "先把有哪些功能和界面交互做好，之后再考虑具体的功能实现"

**实际已经交付的东西**：

| 已实现 | 规模 | 对一个家庭自用、单机 App 的价值 |
|---|---|---|
| FastAPI 服务层 + 6 层中间件（认证 / 限流 / 幂等 / 会话事务 / 访问日志 / request_id） | `api/` 整层，约 26 个接口 | **接近 0**：本机单用户，没有第二个人来限流，也没有重放攻击 |
| 幂等中间件 | 291 行 + 一张表 | **当前完全空转**：客户端每次调用都新生成 UUID，重放永远不会命中（`client.py:880`） |
| 三级限流（含"贵接口"分桶） | 分桶键用**未经验证的** `X-API-Key`（`ratelimit.py:63-69`） | 负价值：绕得过，且桶字典只增不减 |
| 任务状态机 + 协作式取消 + 超时 + job 表 + SSE | `worker.py` 298 行 | 为一个 **10–60 秒**的操做了一整套作业系统；而取消只存在内存里、进程重启即失效（`worker.py:75-95`） |
| SQLAlchemy + Alembic（16 张表）+ JSON 导入 + 等价校验 | `storage/` 10 个文件 + 2 个迁移 | 部分是**真价值**（迁移等价校验很硬），但 16 张表对一个家庭过重 |
| 5 套可切换存储后端 | JSON / DB / HTTP / 内存任务 / 菜谱 JSON | **负价值**：行为不一致（U5）、无双后端对拍测试 |
| 三种导出 + 分享视图 + 游标分页 + 每轮缓存 | `plans.py` / `client.py` | 导出有价值；游标分页与缓存对本项目是负担 |

**判断**：做多本身不是错——**顺序错了**。`08` 规划的 P2 是 **Postgres + Redis + 可观测**。在一个"菜谱 38 道、设计基线还没定稿、三个决策还悬着、数据一致性还有洞"的项目里，继续往下建生产化设施，边际价值是负的。

### 3.2 进度与里程碑

**好的方面**

- 有**真正的里程碑**：`p0-storage`、`p1-api` 两个标签，节点清晰。
- **交接文档质量极高**：`07` 的"踩过的坑"33 条（含 PowerShell 改源码毁中文、`alembic.ini` 必须纯 ASCII、沙箱下 `mkdtemp` 权限、中间件顺序反直觉、跨事件循环连接池……），这是一份**别处买不到**的资产。
- 开发节奏快且可追溯：3.5 小时 8 个提交，每个提交带文档更新。

**不足**

- **里程碑全是技术维度**（存储、API），**没有一个"用户可用"的验收节点**：没有"周日排一次 → 周三看一眼 → 买菜打勾"的端到端人工验收记录。
- **验收口径不可靠**（见 3.3）：把"270 项全绿"当出口标准，但这条标准本身会飘。
- **审计期间代码仍在变**（1897→1994 行）：说明"当前状态"没有冻结过，任何评审都只能是快照——同时暗示存在并行改动、缺少"改前先停服务"的纪律（这一点 `07` 第 2 条其实已经写过）。

### 3.3 质量：真实水平比文档写的低一点，但底子很好

**实测（我自己跑的，不是引文档）**

| 套件 | 文档宣称 | 我实测 |
|---|---|---|
| pytest | "270 项全绿" | **收集 270 条**；一次全量运行 **失败 1 条**（`tests/api/test_jobs.py::test_queue_position_when_something_is_already_running`），另一次全量运行全过，**单独重跑 4 次全过** → **flaky**（`queue_position == 1` 依赖"没有别的任务在跑"） |
| `self_check.py` | 163（JSON）/ 161（DB） | **161 通过 / 0 失败**（默认 DB 模式）✅ 与文档一致 |
| `smoke_app.py` | 189 / 185 | **189 通过 / 0 失败** ✅ |
| `smoke_api_app.py` | 44 | **44 通过 / 0 失败** ✅ |

**质量问题清单**

1. **"项数"不是质量指标。** `116 / 110 / 163 / 165 / 189 / 270` 这些数字是 `check()` 调用计数累加（`self_check.py:41-48`），**不是断言数、不是覆盖率**，而且**动态不可复现**：循环体计入、条件体有时不计（`self_check.py:270,404`）、DB 与 JSON 分支不同（`:332-345`）。同一个脚本在不同后端下 PASS 数都能差几项。
2. **有恒真断言在充数**：`self_check.py:283`（`... or True`）、`:541`、`smoke_app.py:746-747` —— 这三处**永远不会失败**，却计入"161 项"。
3. **关键路径没测**：真实 LLM 链路（所有测试强制 `DEEPSEEK_API_KEY=""`）、`tonight_dislike_*`"这道不吃"**从未被点击过**、API 层的"今天"不注入（见 4 号风险）、进程崩溃后任务卡在 running、并发改同一 (天,餐)、**JSON 后端的完整方案/档案读写完全没有测试**。
4. **日期炸弹**：API 测试的种子周写死 `2026-09-14`（`tests/api/conftest.py:58`），而状态判定用真实今天（`tonight.py:152`）→ **过了 2026-09-21，同一份代码的同一批断言会翻转**（"计划中"变"这周已结束"）。这类"测试随日历变红变绿"是最典型的"测试通过但产品是坏的"。
5. **同类 bug 已经发生过两次**：DTO 少字段导致功能**静默退化**（`07` 踩坑 #25、#30：定住的菜渲染不出来、定住的菜在服务端不生效、来源痕迹全变成"口味档案"、多餐"做完了"刷新即失效）。两次都靠人工发现，**没有自动防线**。

**值得表扬、且应该继续的部分**

- **AST 源码守卫**（`tests/test_meal_slot_guard.py`）：禁止"只比 `.day` 不比 `.meal`"的取数写法。**这是本项目的最高工程水准**——"记得别这么写"不算防线，让机器盯着才算。
- **迁移等价校验**（`verify_migration.py` 18 项）+ 迁移前自动备份。
- **错误文案测试**（`test_error_copy.py`）：不许把框架英文 `Not Found` 甩给用户。
- **踩坑文档化**：33 条，价值超过很多正式文档。

### 3.6 管理动作：三个决策已积压（每个只要 10 分钟）

文档里明确写着"等你点头"，但它们已经挂了一段时间，而且**都在影响代码与测试**：

### 3.7 交付物：缺一个"别人能看懂"的入口

根目录有 `.env.example`、`requirements.txt`、`pytest.ini`、`alembic.ini`，**但没有 `README.md`**。

对一个要拿去求职展示、或交给别人接手（甚至只是自己三个月后回来看）的项目，这是**最高性价比的一个缺口**：8 行字的说明（这是什么 / 怎么装 / 怎么跑 / 文档在哪）就能补上。现在读者只能靠 `docs/README.md` 里的"按目的选读路径"来摸索。

### 3.8 求职视角的一个提醒（因为这是这个项目的真实目的之一）

这个项目的技术故事已经**足够强**（LangGraph 编排 + 确定性校验 + 服务化 + 33 条踩坑 + AST 守卫）。但技术面里几乎一定会被问到：

> **"这是一个家庭自用的排菜工具，你为什么要做限流、幂等、任务队列和多租户？"**

现在这题的答案**只能靠临场圆**。两个选择：① 补一个诚实的说法（"我把它当服务化的练习题，`docs/08/09` 有完整的分阶段验收"）；② 更简单地——**把它砍回目标规模**，让"我做得刚好够用"本身成为一个加分项。**两条路都行，但要有意识地选一条。**

## 5. 不足的方面（分维度总结）
