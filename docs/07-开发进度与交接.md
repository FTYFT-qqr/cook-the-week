## 1.5 数据在哪（后端 P0，2026-09-11）

**默认 `STORAGE=db`：数据在 `data/app.db`（SQLite，WAL）。** 想回到 JSON 文件，一条环境变量即可：

```powershell
$env:STORAGE='json'    # 回退：读 data/recipes.json + saved_plans.json + customer_profile.json
```

| 项目 | 说明 |
|---|---|
| 建库/升级 | `python -m recipe_planner.storage.migrate`（空库 `upgrade head`；`create_all` 建的老库自动 `stamp head`，**不动数据**） |
| 迁移 | `alembic upgrade head` / `alembic downgrade base`；基线 `0001_init`（16 张表） |
| JSON → DB | `python -m recipe_planner.storage.import_json`（先备份到 `data/backup/<时间戳>/`，可重复执行） |
| 等价校验 | `python scripts/verify_migration.py` → 18 项（菜谱逐字段、方案逐天逐菜、档案集合、摘要重算） |
| 保留策略 | 超过 12 周的老方案自动归档（`PLAN_RETENTION_WEEKS`，只标记不删除） |
| 备份 | 迁移前自动备份 JSON；数据库本体备份在 P2（`docs/09`） |

> 数据库文件不进 git（`.gitignore` 已排除 `data/app.db*`、`data/backup/`、`logs/`、`.tmp/`）。

### 1.6 API 服务（P1，27 个接口）

```powershell
& $py -m uvicorn recipe_planner.api.main:app --host 127.0.0.1 --port 8000
```

| 接口 | 说明 |
|---|---|
| `GET /health` · `GET /ready` | 存活 / 就绪（就绪逐项报告 db、redis、llm，DB 不通返回 503） |
| `GET /api/v1/recipes` | 菜谱库（`q` / `category` / `liked=all\|true\|false` / `limit` / `cursor`） |
| `GET /api/v1/plans` | 以前的方案（最新在前，带 `current_id`） |
| `GET /api/v1/plans/current` | **今晚页**：状态①–⑤ + 今晚菜/时间/金额/理由/几点能吃上（没有方案也 200） |
| `GET /api/v1/plans/{id}/tonight?day=N` | **某一版**的今晚页（界面"切到以前的某一版"用）；`day` 是"手动切到第 N 天" |
| `GET /api/v1/plans/{id}` | 方案详情（7 天 + 每日菜 + 清单 + 概览 + 结构统计 + 定住的菜） |
| `GET /api/v1/plans/{id}/days/{day}` | 单天（含下锅顺序） |
| `GET /api/v1/jobs/{id}/events` | **SSE 进度**（`stage…` → `done`/`error`），前端不用轮询 |
| `GET /api/v1/plans/{id}/export/{fmt}` | 带走：`csv`／`txt`／`html`（A4 单页，自带样式） |
| `GET /api/v1/plans/{id}/share` | 分享给家人的干净文本 |
| `GET /api/v1/profile` | 档案（喜欢/不喜欢/评分/来源痕迹/指纹） |
| `GET /docs` | OpenAPI 文档（可交互） |

写入接口（P1-3，统一回执 `{kind, message, data, action_log_id, undo_hint, next_steps}`）：

| 接口 | 说明 |
|---|---|
| `PATCH /api/v1/plans/{id}/days/{day}` | `op` = `skip`／`restore`／`people`（当天**总**人数）／`faster`／`swap`／`replace_day`／`done` |
| `POST /api/v1/plans/{id}/dishes/{day}/{recipe_id}/feedback` | `like`／`dislike`／`lock`／`unlock` |
| `POST /api/v1/plans/{id}/save-money` | 换一道更便宜的，返回省了多少 |
| `POST /api/v1/plans/{id}/rate` | `{day, score}`（2 好吃／1 一般／0 下次不做） |
| `PUT /api/v1/plans/{id}/shopping/checks` | 幂等，全量覆盖 |
| `POST /api/v1/plans` | **排一周（异步）**：立刻回 `202 + job_id`，进度看 `/jobs/{id}` 或 SSE |
| `GET /api/v1/jobs/{id}` · `GET /api/v1/jobs` | 任务状态 / 最近任务（排障） |
| `POST /api/v1/jobs/{id}/cancel` | 取消（排队中立刻；运行中下一个节点停） |
| `PUT /api/v1/profile` · `POST /api/v1/profile/clear?confirm=true` | 档案增删（清空必须二次确认，否则 409）；`source` 让界面记下"这条偏好是在哪点的" |
| `PUT /api/v1/profile/restore` | **整份恢复**（只给"撤销上一步"用：喜欢+评分+来源痕迹一起回来，否则是假撤销） |
| `DELETE /api/v1/plans/{id}?confirm=true` | 删除某一版（缺 confirm → 409；`undo_hint=None`，删掉找不回来） |

错误统一 `application/problem+json`：`{code,message,request_id,status,details.next_steps}`，
`message` 一律人话，`next_steps` 给可点击的下一步（05 §5.1）。
写入一律"改一处只动一处"（R1），`undo_hint` 是**精确逆操作**（拿它原样再发一次即可回退）。

## 3. 页面结构与交互（05 基线）

左栏任务栏 **5 项**，默认落在「今晚」：

| 页 | 要点 |
|---|---|
| **今晚**（默认首页） | 主角大卡（`今晚 · 周三 9/17` / 菜名 22px / `约 45 分钟 · 预计 ¥62` / 一句理由 / 可选「几点能吃上」）+ 每道菜一行`这道不吃` + 两个整卡级快改`回家晚了`/`来客人了` + `做完了`/`开始做饭`；**五种状态**：①有安排 ②已跳过 ③已做过（含打分）④还没有菜单（引导卡）⑤这一周已结束 |
| **本周计划** | 顶部方案名+`重排一版`/`改需求`；`哪里能省`/`都满意`/`分享视图`；7 个等宽天行（今天高亮、已过只读、已跳过显示`不做饭`）；每日详情（逐道卡 + `换一道`/`定住`/`喜欢`/`不喜欢` + 下锅顺序）；`以前的方案`（切版/照上一版/删除） |
| **排一周** | 三张场景卡 + 四组表单（人数与天数 / 口味与忌口 / 时间与预算 / 家里已有）+ `生成菜单`；阶段反馈可取消；首次排完落「今晚」、重排落「本周计划」 |
| **买菜清单** | 到店模式（一行一样、点一下打勾、已买沉底变淡、勾选**写进存档**）+ `分两次买`（周初耐放/周中新鲜）+ 单菜小料标`可选` + `带走清单`（CSV / 文本 / A4 打印） |
| **口味档案** | 喜欢/不喜欢两个可编辑列表 + 来源痕迹（`8/10 在菜单里点的`）+ 就地说明 + `导出档案`/`清空`/隐私说明 |

**八条不变量（05 §4）**均已落地：单点改动只影响单点、动作有回执且可撤销、破坏性操作二次确认、
改不了就给可点击的下一步、结果可复现（temperature=0）、忌口永不妥协并明说"已避开"、数字都带口径、状态永远可见。

## 4. 关键接口速查

- 约束：`UserConstraints(people, days, dishes_per_day, allergens, spice_level, taste_tags, goal, max_time_min, skill, cook_start, budget_per_person_day, pantry_items, liked_dishes, disliked_dishes, must_include_recipes)`
- 计划：`DayPlan(day, meal, dishes, skipped, people)`（`people` =  "来客人了" 的单日份量）
- 单点操作：`swap_dish / replace_in_day / skip_day / restore_day / fastest_day / cheapest_swap / protein_swap / veg_swap`
- 词匹配换菜：`recipes_matching / candidates_matching`；刷新：`refresh_result`
- 存档：`store.save_plan / update_result / previous_record / delete_record / set_done / set_checked / today_index`
- 档案：`prof.set_feedback(name, action, known, source=) / rate(name, score) / feedback_origin / rating_of`
- 报告：`rep.plan_summary / day_minutes / cook_order / structure_line / shopping_csv / shopping_text / printable_html / share_text / split_batches`
- 单点写入（服务端唯一实现处）：`actions.skip / restore / set_people / faster / swap / replace_day / mark_done / feedback / rate / save_money / set_checks`
  → 统一 `ActionOutcome{kind, message, days, profile, extra, undo, next_steps}`；路由用
  `actions.apply_to_result(record, outcome, db)` 落库（**必须走它**，否则换了菜忘了重算清单）

## 6. **踩过的坑（接手前务必看）**

1. **绝不要用 PowerShell / 脚本改源码**：`Get-Content -Raw` + `Set-Content` 会按 GBK 解码 UTF-8，**毁掉中文**（本项目已因此损坏过 `app.py`，靠 `git checkout` 才救回）。文本改动一律用 edit/write 工具。
   **这台机器上跑的是 Windows PowerShell 5.1**：即使加了 `-Encoding UTF8`，`Set-Content` 也会**加上 BOM**、并把**整个文件的行尾改成 CRLF**（我犯过一次，用 python 按 `utf-8-sig` 读取 + 换行规范化才修回）。行尾差异会被 git 的 `autocrlf` 掩盖，BOM 不会 —— 别赌。
   **python 一行脚本也一样会中招**：`Path.write_text()` 默认按 Windows 换行写，`read_text()` 又把 CRLF 读掉 —— 一次 `.replace()` 回写就会把整个文件变成 CRLF（第二次翻车）。
   真要改就用 edit/write 工具；万不得已要规范化行尾，用 `read_bytes()`/`write_bytes()` + 显式 `.replace(b'\r\n', b'\n')`，并**改完立刻扫一遍**：
   ```powershell
   & $py -c "import pathlib;root=pathlib.Path(r'D:\cook\recipe-planner');print([str(p) for p in root.rglob('*.py') if p.read_bytes()[:3]==b'\xef\xbb\xbf' or b'\r\n' in p.read_bytes()])"
   ```
   顺带一个坑：`[System.IO.File]::ReadAllBytes('相对路径')` 用的是**进程**工作目录，不随 PowerShell 的 `cd` 变，会读到一个不存在的位置；.NET 调用一律给绝对路径。
2. **改 `app.py` 前先停 Streamlit**，否则写入报 `ReplaceFileW EIO (Win32 1175)`；**启动前确认端口空闲**，否则 `Port … is not available` 而你以为服务在跑。
   **这个坑我踩了两次**：uvicorn/streamlit 因端口被占直接退出（日志只在 stderr 里一行），
   而旧进程还在应答 —— 于是"接口 404 / 页面没变化"被误判成新代码的 bug。
   **起完服务必须验一下它是不是新进程**：`Invoke-WebRequest http://127.0.0.1:8000/openapi.json`，
   看有没有本次新加的路由（例如 `/api/v1/jobs`）；Streamlit 则看新功能是否出现。
3. **AppTest 的坑**：*元素引用在 rerun 后失效*（每次重新取）；`at.session_state` **没有 `.get()`**（用 `"k" in at.session_state`）；checkbox 用 `.check()`；按钮的 `type` 是字符串；同页多个 toggle 要**按 key 过滤**再操作；`st.progress/st.toast/st.code` 可能不被 element_tree 解析（断言要宽容）。
4. **widget key 不能在实例化之后写**：需要程序化改控件值时统一挂 `session_state["pending_sync"]`，脚本开头再 `_sync_widgets_from_inputs`。
5. **勾选/清空的 key 用 epoch**：`chk_{epoch}_{name}`，清空 = `epoch += 1`（不要直接改已实例化的 widget key）。
6. `data/recipes.json` 里 `调料/其他` 类食材不进采购清单；份量按 `people/2` 折算（菜谱是 2 人份基准）。
7. **`alembic.ini` 必须是纯 ASCII**：Alembic 用**系统 locale 编码**读这个文件，本机是 GBK，写中文注释会直接 `UnicodeDecodeError` 起不来（其它文件不受影响，正常写中文）。
8. **本机沙箱下 `os.mkdir(path, 0o700)` 建出的目录连列都列不了**（`WinError 5`），而 `tempfile.mkdtemp` 把 `0o700` 写死了 → Streamlit/AppTest 的临时目录建完就用不了、退出时也删不掉，`atexit` 打出一串 `PermissionError`（**看着像回归失败，其实断言早全过了**）。`scripts/smoke_app.py` 开头已把 `mkdtemp` 换成"默认权限"版本修掉它。历史遗留的 `\.tmp\tmp*` 目录在本会话内删不掉（`takeown`/`icacls`/`rd` 全被拒），只能在本沙箱之外删。
9. **别在数据库线程里调同步门面**：`sync_bridge.run()` 从数据库线程再提交协程会死锁（已加显式报错拦住）。导入时算档案指纹用的是同 session 内的 `_profile_sig_in_session`，不要改回去。
   反过来（P1-5 的任务）**可以**在工作线程里调 `sync_bridge.run()`：那不是数据库线程，是另一条线程。
10. SQLite 的 `ON DELETE CASCADE` **默认不生效**，必须靠 `attach_sqlite_pragmas()` 打开 `foreign_keys=ON`；生产 engine 和测试都要挂。
10.5 **别让一个 engine 的连接池跨越两个事件循环**：排菜任务在后台线程里跑，它通过 `sync_bridge` 用自己的
    事件循环写库；连接池会把在 A 循环里建的连接交给 B 循环 → `attached to a different loop`。
    文件型 SQLite 已改成 `NullPool`（用完即关）。`tests/api/test_jobs.py` 就是这条的护栏。
11. **中间件顺序（Starlette 反直觉）**：`add_middleware` 是**后加的在最外层**；而注册的**异常处理器在最内层**。
    后果：路由抛出的领域异常会被就地转成 4xx/5xx 响应，外层的 Session 中间件**根本看不到异常** ——
    所以它必须**按响应码判定**（≥400 回滚、否则提交），不然"出错的请求"照样会被提交。
    也因为这个，认证/限流/幂等这些**在异常处理器外层**的中间件发不了 `JSONResponse`，只能用
    `errors.send_problem()` 自己发 ASGI 消息。
12. **路由里不要调 `store.*` / `profile.*` / `db.load_db()` 这些同步门面**：它们内部走 `sync_bridge.run()`，
    而请求本身就在事件循环里，再往里塞协程会直接报错。服务端一律用 `storage/async_adapters.py`。
13. **pytest 抓不到我们自己的日志**：`setup_logging()` 的 handler 在 import 期就绑定了当时的 `sys.stdout`，
    `capsys` 换掉 `sys.stdout` 之后它照样往老对象写（`capfd` 也未必灵）。
    要断言日志就**自己挂一个 handler、在 `emit` 里立刻格式化**（`tests/api/test_middleware.py` 的 `_JsonCollector`）。
14. **测 500 的响应体要 `httpx.ASGITransport(app=..., raise_app_exceptions=False)`**，
    否则异常会被抛到测试里、看不到 problem+json。代价是真崩溃也会变成 500，所以每条断言都要写清状态码。
15. **测试要改环境变量时，必须在那之后再 `create_app()`**：中间件在构造时就读取了设置
    （`monkeypatch.setenv` 写在测试体里，比 fixture 里已经建好的 app 晚）。
16. **幂等键要按端点分开存**：`idempotency_key` 表主键只有 `key` 一列，所以存进去的是
    `sha256(端点 + 客户端 key)`；直接存客户端给的 key，同一个 key 用在两个接口上会互相回放。
17. `profile` 的 `ratings` 形状是 `{菜名: {"score": 0|1|2, "date": "MM/DD"}}`（由 `profile.rate()` 定），
    不是 `{菜名: 2}`；`history` 里是 `{"since": "MM/DD", "source": "在哪点的"}`。写测试数据时别再猜。
18. `tests/api` **不是包**（没有 `__init__.py`）：`from .conftest import …` 会失败，
    要么用夹具传函数，要么 `from conftest import …`（pytest 会把该目录放进 `sys.path`）。
19. **PowerShell 5.1 传参遇到双引号会把参数拆碎**：`git commit -m $msg` 里只要有一处 `"`，
    整段消息就会被切成好几个参数，git 报一串 `pathspec … did not match any file(s) known to git`（提交根本没发生）。
    写长中文提交信息一律**写文件 + `git commit -F 文件`**。
20. **写测试时别用"我构造的数据"当断言前提**：这轮我把"便宜菜"定义错了（以为 r4 不便宜）、
    把"周二 22:30 会切到周三"算成了第 4 天、把 SSE 阶段数当成固定值 —— 几次失败全是**测试假设错**，代码是对的。
    先照着实现读一遍再写断言，比事后调试便宜。
21. **服务端客户端的前缀只能在唯一一处拼**：第一版 `client._request` 用 `path.startswith("/")` 判断"是不是绝对地址"，
    结果 `/plans` 被当成绝对地址 → **整片接口 404**。现在 `path` 默认相对 `/api/v1`，根上的探针接口显式 `root=True`。
22. **别把框架的英文 detail 透给客户**：Starlette 自己抛的 404/405，detail 就是标准英文短语，
    `detail or message` 这种写法会把 `"Not Found"` 直接摆到客户面前。判据：detail 等于
    `HTTPStatus(status).phrase` 时**不用它**（`tests/api/test_error_copy.py` 三条用例守着）。
23. **`USE_API=1` 时界面不许再打开数据库**：`db.load_db()` 原来只看 `STORAGE`，会在**界面进程**里建连接池 ——
    服务化之后库是服务端的。现在 `USE_API=1` 一律读随应用发布的 `data/recipes.json`（静态资源）。
24. **服务端已经存好的东西，界面不要再存一份**：排菜任务在服务端把方案存好并给回 `plan_id`，
    界面的 `_ensure_plan` 直接用 `job.record`。还有个坑：**"上一版"必须在提交任务之前读** ——
    任务做完再 `latest_record()`，拿到的就是刚存下的这一版，回执里会写错"另存为新的一版"。
25. **DTO 少一个字段 = 功能静默退化**（这一轮踩了三次）：`ConstraintsOut` 少了 `must_include_recipes`，
    "定住的菜"就渲染不出来；`PlanCreateIn` 少了它，定住的菜在服务端排菜时**根本不生效**；
    `ProfilePatchIn` 少了 `source`，所有人的来源痕迹都退化成"口味档案"，05 M5 那句"8/10 在哪点的收藏"就没了。
    加接口/改 DTO 时，对着"界面到底用了哪几个字段"过一遍。
26. **FastAPI 的类型提示写在函数体里会变成 422**：局部 `from fastapi import Request` 让 `Request` 成了局部名字，
    FastAPI 解析不到类型提示，就把 `request` 当查询参数 → 422。`Request` 必须**模块顶层**导入。
27. **pytest 的 `tmp_path` 在这台机器上用不了**：它内部走 `tempfile.mkdtemp`（0o700 建目录），
    沙箱令牌连列都列不了 → fixture setup 阶段直接 `PermissionError`。仓库里一律用**仓库内**的 `.tmp/`
    （`tests/api/conftest.py`、`scripts/smoke_app.py`、`tests/test_client.py` 都是这么做的）。
28. **`pytest -q -q` 会吞掉最后的汇总行**（数不出用例数）。`--collect-only -q` 输出的是"每个文件多少条"，
    加起来才是总数。
29. **"一天一顿"这个假设散落在全项目 —— 改维度时必须一处不落地过一遍**（多餐那一轮最贵的教训）。
    一天多顿之后，`next(p for p in result.days if p.day == X)` 会**静默拿到当天第一顿（早餐）**：
    不报错、不返回 None、界面看着完全正常，只是全错。第②步替换了 `core` 里 7 处、第③步改了界面、
    第④步改了存储 —— **唯独漏了 `api/routes/` 这一层**，于是用户看到"早中晚三餐显示的都是一样的"。
    现在有一道 **AST 源码守卫**（`tests/test_meal_slot_guard.py`）扫全项目，命中就红：
    只比较 `.day`、不比较 `.meal` 的 `next(...)` 一律拦下（例外写 `# noqa: meal-slot`）。
    **教训**：同一维度的取数口子要**收敛成一个函数**（`PlanResult.slot/slots_for`、`core.slot_of`），
    并且"记得别这么写"不算防线 —— 得让机器盯着。
30. **接口少回一个字段，功能就静默退化**（第 25 条的续集）：`PlanDetailOut` 只回 `done_days`
    （"那一天做完了"这种只做晚餐时的老表达），不回 `done_slots` → 客户端还原不出"哪一顿做完了"，
    "做完了早餐"刷新一次就变回没做。**改存储维度时，同步对一遍 DTO 与客户端回读。**
31. **校验脚本别把"基线"和"现状"比相等**：`verify_migration.py` 原来断言"JSON 方案数 == 库方案数"，
    用户随手多排两版后这里必然变红（JSON 那份是**冻结的迁移基线**）。改成校验
    "**JSON 里每一份方案都还在库里**"（迁移没丢东西），库里多出来的新方案点名打印、不参与比对。
