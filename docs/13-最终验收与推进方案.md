## 0. 结论先行

项目的**本机家庭使用主链路已经可交付**，但还不能称为“最终收尾完成”。更准确的完成度是：

| 口径 | 当前状态 | 结论 |
|---|---|---|
| 核心产品链路 | 五页任务流、全天菜单、买菜清单、偏好、撤销、做法、双存储均已落地 | **可演示、可本机使用** |
| 自动化基线 | 2026-09-16 重新实跑七套门禁，全部退出码为 0 | **当前基线稳定** |
| `12` 的理想功能 | 10 项中 **5 项完成、3 项部分具备、2 项主动延后** | **阶段零～三完成；阶段四未开始；阶段五需拆分评估** |
| 工程收尾 | 临时文件持续增长；服务化链路仍有幂等、终态、任务恢复、缓存与过渡桥问题 | **未完成** |
| 文档与仓库卫生 | 历史数字保留为带日期快照；外部工具/个人交付物已通过忽略规则明确归属 | **A5 已完成，未删除用户资产** |
| 本文执行进度 | A1–A6 已完成；B/C 阶段按条件或后续版本推进 | **A 阶段 6/6 已完成** |

因此，当前发布判断应写成：

> **本机单用户版达到候选交付状态；完成 A 阶段并通过人工验收后，才可标记为 v1 收尾完成。**
> B 阶段决定服务化模式是否也能称为稳定；C 阶段属于下一版产品能力，不阻塞 v1。

不要再用一个笼统百分比概括整个项目。MVP、工程收尾、理想功能是三条不同基线，混成一个数字会掩盖风险。

```powershell

$env:PYTHONUTF8 = '1'
$env:PYTHONIOENCODING = 'utf-8'

& $py -m pytest tests
& $py scripts\self_check.py
$env:STORAGE = 'json'; & $py scripts\self_check.py; Remove-Item Env:STORAGE
$env:SMOKE_STORAGE = 'json'; & $py scripts\smoke_app.py
$env:SMOKE_STORAGE = 'db'; & $py scripts\smoke_app.py; Remove-Item Env:SMOKE_STORAGE
& $py scripts\smoke_api_app.py
& $py scripts\verify_migration.py
```

| A4 | 回填当前文档口径 | `docs/README.md`、`05`、`07`、`08`、根 README | 当前入口不再给出互相冲突的事实；历史实施记录保留并标为历史快照 |

### B 阶段 · 服务化稳定（预计 2–4 天）

执行顺序：**B-04 终态回查 → B-05 缓存边界 → B-03 任务收尾 → B-01/B-02 中间件决策 → B-06 拆桥 → B-07 导出文案**。

这个顺序先保证“服务端实际结果与界面一致”，再做架构收敛。原方案把“拆桥”放在所有服务化缺陷之前，
会同时改动九个界面入口和不稳定的任务链路，回归面过大。

统一验收：

- 模拟 SSE 断流后，客户端能拿到服务端最终状态；
- 服务重启后没有永久 `queued/running` 任务；
- 两个并行会话不会互相污染缓存对象；
- 同一个逻辑提交重试不会生成两份方案；
- `client.py` 最终不再包含 `_day_patches` / `update_result` 过渡实现；
- 七套门禁和 `USE_API=1` 人工闭环均通过。

### C 阶段 · 下一版能力（按反馈排期）

1. **先做 C-01 结构策略**：只选 2–3 个真实场景，分别定义输入、可量化结构指标和解释文案；
2. **再做 C-02 MMR**：它是排序改进，不依赖外部内容，不与策略层一次合并；
3. **最后小批量做 C-03 视频策展**：直链失效必须可检查，搜索入口继续作为兜底；
4. C-04 只有出现真实需求后再进入设计。

阶段四的验收不能只写“两个策略结果不同”，因为随机性也能造成不同。至少要验证：

- 老人场景的辣菜比例和高难度菜比例不高于默认场景；
- 减脂场景每餐满足定义好的蔬菜/蛋白结构；
- 省钱场景的食材复用率提高，且总价不升高；
- 无法同时满足时明确告诉用户放宽了哪一条，而不是静默违约。
