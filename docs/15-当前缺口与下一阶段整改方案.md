### F-02 重构迁移等价验证

#### 当前问题

`scripts/verify_migration.py` 同时承担了两个互相冲突的目标：

- 证明当初 JSON → SQLite 的迁移没有丢数据；
- 要求继续使用中的 SQLite 档案永远等于冻结的 JSON 档案。

方案部分已经允许数据库比 JSON 多，但偏好部分仍要求集合完全相等。用户在数据库模式里正常点击喜欢或不喜欢后，
门禁必然失败。这不是迁移回归，而是验证对象选择错误。

#### 建议改法

把验证拆成两条：

1. **固定快照迁移测试**
   - 在 `tests/fixtures/migration_baseline/` 保存最小、脱敏、可跟踪的菜谱/方案/档案 JSON；
   - 每次创建新的 `.tmp/migration-*/app.db`；
   - 对临时数据库执行迁移和 JSON 导入；
   - 对菜谱、方案、勾选、完成状态、偏好、评分逐字段比较；
   - 测试结束精确清理主文件及 `-wal/-shm`。

2. **真实数据只读审计**
   - 另设 `scripts/audit_live_data.py`；
   - 只检查当前数据是否可读、外键是否完整、是否存在未知菜谱或损坏记录；
   - 不要求 SQLite 与旧 JSON 继续相等；
   - 不写入、不修复真实数据。

`scripts/verify.ps1` 应调用固定快照迁移测试。真实数据审计可以单独执行，但不得成为“两个后端当前内容完全相等”的假门禁。

建议涉及：

- `scripts/verify_migration.py`
- `scripts/verify.ps1`
- `tests/test_migrations.py`
- `tests/fixtures/migration_baseline/`
- 根 `README.md` 中迁移验证说明

验收：

```powershell

```

- 统一验证完整退出码为 0；
- 连续运行两轮结果一致；

## 4. Q 类：推荐质量与跨周轮换

### Q-01 强化离线评估门禁

当前评估报告是有效的第一版基线，但还有两个问题：

1. `reason_is_consistent()` 与理由生成器共享同一套输出模板，100% 更接近“实现自洽”，不是独立事实验证；
2. 脚本虽然报告周内重复、预算和目标命中，但当前退出码只由硬约束与理由一致率决定。

整改要求：

- 理由验证按独立事实检查：时间、成本、标签、蛋白质数据、偏好分值分别断言；
- “补蔬菜”只允许用于非蛋白菜，“先安排蛋白来源”只允许用于蛋白菜；
- 周内重复数大于 0 时门禁失败；
- 设置预算的场景出现无说明超预算时门禁失败；
- 目标方向命中率低于固定基线时门禁失败；
- R2 完成后，默认跨周重合率大于 60% 时门禁失败；候选不足场景必须单独标记，不可混入默认阈值。

建议涉及：`scripts/evaluate_recommendations.py`、`tests/test_recommendation_quality.py`。

### Q-02 实施近期食用惩罚

当前 `rotation_bonus()` 对 14 天内吃过的菜返回 0，因此同样输入连续两周仍得到相同结果。离线报告中八个场景的
跨周 Jaccard 均为 **100%**，这正是 R2 应解决的问题。

建议将其升级为 `rotation_adjustment()`，初始实验值：

| 距上次真实食用 | 调整分 |
|---:|---:|
| 0–2 天 | `-3.0` |
| 3–6 天 | `-1.5` |
| 7–13 天 | `-0.5` |
| 14–29 天 | `+0.75` |
| ≥30 天 | `+1.5` |
| 从未吃过 | `0` |

这些数值必须通过固定场景验证后再定版。明确喜欢可以抵消部分近期惩罚，但不得覆盖过敏、永久不喜欢等硬约束。

建议涉及：`recipe_planner/preference.py`、`recipe_planner/core.py`、`tests/test_eating_history.py`、离线评估脚本。

完成定义：

- 近期吃过场景与默认场景不再完全相同；
- 默认连续两周重合率达到约定目标；
- 40 天前吃过仍得到小幅正向轮换；
- 无吃过记录时保持既有行为；
- JSON/SQLite 行为一致。

### Q-03 增加“这周先别排”

保留现有永久“不喜欢”，新增事件：

- `snooze`：未来 7 天或本周临时排除；
- `unsnooze`：提前恢复。

`dish_event.action` 已允许扩展词表，第一版不必新增数据库列。界面必须用不同文案表达：

- “这周先别排”：自动到期；
- “不再推荐”：永久进入不喜欢列表。

检索优先级：硬约束 → 永久不喜欢 → 有效临时避开 → 近期食用调整 → 其他软偏好。

完成定义：有效期内排除、到期恢复、可提前撤销、两种存储一致、档案页能说明生命周期。

### Q-04 校正事件语义

事件必须区分：

| 事件 | 含义 | 推荐权重 |
|---|---|---:|
| 系统初次排入 | 曝光 | 0 |
| 用户主动换回/选择 | 接受 | 弱正向 |
| 做完、评分 | 实际食用 | 正向或负向反馈 |
| 喜欢/不喜欢 | 明确态度 | 强正向/硬排除 |

复核所有 `SELECT` 写入位置，禁止把系统自己生成的菜当作用户喜欢，避免算法强化自己的历史输出。

### Q-05 精简 AI 返回结构

当前 `llm_planner.build_prompt()` 仍要求模型为每道菜生成理由，但 `llm_plan()` 解析完成后会把这些理由全部丢弃，
再用 `make_reason()` 重建。模型生成这部分文本不会进入最终产品，只增加 token、响应时间和格式出错概率。

建议将模型输出收敛为纯菜单结构：

```json
{
  "days": [
    {
      "day": 1,
      "meal": "晚餐",
      "recipe_ids": ["r01", "r12"]
    }
  ]
}
```

单餐模式可以继续省略 `meal`，但内部解析后仍统一转换为现有 `DayPlan` / `ChosenDish`。每个 `ChosenDish.reason`
只由 `make_reason()` 和实际结构规则生成。

整改要求：

- 从提示词删除“每道菜给出理由”的要求；
- 修改 JSON 示例和 `_parse_plans()`，只接受候选菜谱 ID、天数与餐次；
- 严格拒绝候选池外 ID、重复 ID、缺失餐次和错误道数；
- 保持 `validate → repair → deterministic fallback` 不变；
- 修正测试 fixture，不再伪造模型理由；
- 增加用量对比：同一固定场景记录修改前后的请求字符数、响应字符数和耗时；
- 不把实际 API key、完整用户偏好或原始响应写进日志。

建议涉及：

- `recipe_planner/llm_planner.py`
- `tests/test_meals_plan.py`
- `scripts/smoke_llm.py`
- 根 `README.md` 的 AI 能力说明

验收：

1. 模型返回只有菜谱 ID 的合法 JSON 时可以生成完整菜单；
2. 最终每道菜仍有确定性、可核对的理由；
3. 模型返回自编 ID、重复 ID 或错误数量时会被拒绝并安全降级；
4. 不配置密钥时既有确定性路径完全不变；
5. 提示词和响应体积低于修改前基线；
6. 全部离线门禁与一次显式授权的真实模型冒烟通过。

#### AI 的职责边界

AI 可以：

- 把原始菜谱转换成统一 `Recipe` JSON；
- 统一食材名称和单位；
- 把长做法整理成 3～5 步；
- 建议口味、烹饪方式和场景标签；

- 过敏原是否安全；

### C-02 菜谱数据库主源设计

#### 当前状态

项目并不是“完全没有数据库”，而是处在 JSON → SQLite 的过渡状态：

- `recipe` / `ingredient` 表已经存在，默认 `STORAGE=db` 时领域层会从 SQLite 读取；
- `RecipeRepo.upsert_many()` 已能按菜谱 ID 幂等导入；
- `import_json.py` 会把 `recipes.json` 一次性导入数据库；
- `GET /api/v1/recipes` 已从服务端菜谱仓储读取；
- 但菜谱内容仍以 `data/recipes.json` 为人工维护源；
- `USE_API=1` 时，界面进程的 `load_db()` 仍强制读取本地 JSON；
- API 目前只有菜谱查询，没有受控的新增、审核、发布和归档流程。

2026-09-20 实测进一步确认：`data/recipes.json` 为 127 道，而当前 `data/app.db` 的 `recipe` 表仍为
100 道；迁移 head 仍是 `0004`。因此 C-02 不是文档层面的潜在风险，而是已经存在的内容版本分叉。

因此现在的核心风险是“双主源”：JSON 和数据库可以在同一时间各自变化，最终出现内容不一致。

#### 目标架构

```text
人工/AI 草稿
    → staging 导入与校验
    → SQLite recipe/ingredient（唯一运行时主源）
    → 本地模式直接读取 RecipeRepo
    → API 模式通过 /api/v1/recipes 读取
    → 可选导出只读 JSON 快照，用于初始化、审查和备份
```

数据库成为运行时唯一真相来源；JSON 降级为：

- 新安装时的种子数据；
- 可读的版本审查快照；
- 导出/备份格式；
- 自动化测试 fixture。

不得再同时允许人工修改 JSON 和数据库，并期待两边自动保持一致。

#### 建议表结构

保留现有 `recipe` 与 `ingredient`，不要为了 100～500 道菜过度拆表。建议通过下一次 Alembic 迁移补齐：

`recipe` 新增字段：

| 字段 | 用途 |
|---|---|
| `carbs_g` / `fat_g` | 补齐领域模型已有但 ORM 尚未持久化的营养字段 |
| `status` | `draft/review/published/archived`，只有 `published` 进入推荐 |
| `version` | 菜谱内容版本，修改时递增 |
| `source_type` | `family/book/website/video/ai_draft` |
| `source_url` / `source_creator` | 来源追踪 |
| `reviewed_at` | 人工复核时间 |
| `nutrition_basis` | `per_serving/per_100g/unknown` |
| `nutrition_source` | 营养数据来源说明 |
| `nutrition_estimated` | 是否为估算值 |
| `content_hash` | 判断导入内容是否真的变化 |
| `created_at` | 与现有 `updated_at` 配对 |

现有 `taste_tags`、`goal_tags`、`allergens`、`steps` 可继续使用 JSON 列。当前规模下无需立即建立复杂标签关联表。

新增 `recipe_reference`：

| 字段 | 用途 |
|---|---|
| `id` | 主键 |
| `recipe_id` | 关联菜谱 |
| `kind` | `video/article/search` |
| `platform` | B站/小红书/抖音/网站等 |
| `title` / `creator` | 人工可核对信息 |
| `url` | 原始外部链接 |
| `checked_at` | 最后人工打开确认时间 |
| `active` / `sort_order` | 失效控制与展示顺序 |

这样可以逐步替代单一 `video_url`，同时保留旧字段作为迁移兼容层。

可选新增 `recipe_revision`，以 JSON 快照记录每次发布前后的内容、修改原因和审核人。第一版如果只有单人维护，
可以先用导出快照和 Git 审查代替，不必立即实现完整后台审计系统。

#### 仓储与领域层

扩充 `RecipeRepo`：

```text
list_published(filters, pagination)
get(recipe_id)
upsert_draft(recipe, source)
publish(recipe_id, expected_version)
archive(recipe_id, expected_version)
export_snapshot()
```

关键规则：

- 推荐、档案和计划只能读取 `published` 菜谱；
- 菜谱被历史方案引用后不物理删除，只能 `archived`；
- 更新使用 `version` 做乐观锁，避免两个导入批次互相覆盖；
- 食材更新继续在一个事务里替换；
- `content_hash` 相同的重复导入不产生新版本；
- `carbs_g` / `fat_g` 必须贯通 ORM、领域模型、API schema、导入和导出。

#### 本地模式与 API 模式统一

本地模式：

```text
app → load_db() → RecipeRepo.load_db(published_only=True)
```

API 模式：

```text
app → client.load_recipe_db() → GET /api/v1/recipes → 服务端 RecipeRepo
```

需要扩充 `RecipeOut`，返回界面真正需要的完整内容，包括：

- 营养字段；
- 食材克数；
- 文字步骤；
- 参考链接；
- 菜谱版本。

客户端可以按 `catalog_version` 或 ETag 缓存，但缓存失效必须以服务端版本为准。完成后，`USE_API=1` 的界面进程
不再读取 `data/recipes.json`，从根源上消除两端菜谱不同步。

#### 内容写入方式

第一版不建议开放浏览器管理后台或公共写 API。优先提供受控 CLI：

```text
python -m recipe_planner.content.import_batch --file data/staging/recipes.jsonl --dry-run
python -m recipe_planner.content.import_batch --file data/staging/recipes.jsonl
python -m recipe_planner.content.publish_batch --batch <id>
python -m recipe_planner.content.export_snapshot --output data/recipes.snapshot.json
```

流程：

1. `--dry-run` 输出字段、重复、过敏原、来源和引用完整性问题；
2. 正式导入只写 `draft/review`；
3. 人工确认后 `publish`；
4. 发布事务成功后生成可读 JSON 快照；
5. 任一步失败都不改变当前已发布菜谱。

未来如果增加管理 API，必须启用认证、权限和审计；不能复用当前默认 `AUTH_MODE=off` 的本机接口直接开放写入。

#### 初始化与兼容迁移

建议分两次迁移，降低一次变更的回归面：

1. `0005_recipe_catalog_fields`
   - 增加碳水、脂肪、状态、版本、来源和营养元数据；

新安装流程：


SQLite 已足够当前单机规模，不需要因为数据库化立即上 Postgres。需要补齐：

- 发布前自动备份 `app.db`；

#### 验收标准

- 当前 127 道菜迁移前后逐字段一致；

- 修改 JSON 文件不会影响已发布数据库内容；
- 未发布草稿不会进入推荐候选池；
- 被历史方案引用的菜谱只能归档，不能物理删除；
- 同批导入失败时数据库没有部分写入；
- 发布后可以导出可读、可重新导入的 JSON 快照；
- 空数据库可以通过迁移和 seed 恢复；
- 完整 `verify.ps1` 连续两轮通过，真实用户数据哈希不变；
- `13` 的迁移验证按 F-02 使用隔离 fixture，不再拿实时 JSON/DB 内容强行相等。
