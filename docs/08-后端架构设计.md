## 0. 结论先行

| 决策 | 选择 | 理由 |
|---|---|---|
| 语言/框架 | **FastAPI**（async）+ pydantic v2 | 与现有 pydantic 模型同源；自带 OpenAPI；async 与 LLM/DB IO 契合 |
| ORM/迁移 | **SQLAlchemy 2.0（async）+ Alembic** | 一套模型同时跑 SQLite 与 Postgres，P0→P2 只换 URL |
| 数据库 | **P0/P1：SQLite(WAL)** → **P2：Postgres 16** | 家庭并发≈1，先不引入运维负担；表设计按 Postgres 标准写，切换零改表 |
| 缓存/队列 | **P0/P1：进程内实现（可关闭）** → **P2：Redis** | 抽象成 `CacheBackend`/`QueueBackend` 两个接口，实现可换 |
| 前端 | **保留 Streamlit，改为调 API** | 现状界面已验收，不动 UI；`USE_API` 开关可回退直连 |
| 账号体系 | **P3（表结构预留 household/user）** | `01`/`05` 现在是"一台设备一份家庭档案"，做账号需先改基线（见 §9） |

**分层**：`Streamlit / React` → `API 客户端` → `FastAPI 路由` → `中间件栈` → `领域层（现有 core/graph/reporting/assistant）` → `Repository` → `DB / Cache / Queue`。

## 1. 目标与非目标

**目标**
1. 数据可持久化、可查询、可备份：菜谱库、方案（周）、偏好、评分、勾选、任务、操作流水全部进库；
2. 把"排一周"从"前端线程"变成**服务端异步任务**（可观测、可取消、可重试、幂等）；
3. 中间件提供工程底座：请求追踪、结构化日志、认证、限流、幂等、统一错误、缓存；
4. 保留现有领域层、界面层与服务化测试的全部断言（领域层与界面行为不回退）。

**非目标（本期不做）**
- 不做 React 重写（P3 起再评估）；
- 不做多租户计费/运营后台；
- 不引入 Kafka/对象存储/服务网格（家庭场景用不上）；
- 不做精确营养计算（`01` 已声明）。

### 3.2 核心 DDL（Postgres 语法；SQLite 差异见 3.4）

```sql
create table recipe (
  id           text primary key,
  name         text not null,
  category     text not null default '热菜',
  description  text not null default '',
  difficulty   text not null default '简单',
  time_min     int  not null check (time_min between 1 and 300),
  cost_yuan    numeric(8,2) not null default 0,
  calories     int,
  protein_g    numeric(6,1),
  spice_level  text not null default '不辣',
  taste_tags   text[] not null default '{}',
  goal_tags    text[] not null default '{}',
  allergens    text[] not null default '{}',
  updated_at   timestamptz not null default now()
);
create index recipe_tags_idx on recipe using gin (taste_tags, goal_tags, allergens);

create table ingredient (
  recipe_id text not null references recipe(id) on delete cascade,
  seq       int  not null,
  name      text not null,
  amount    text not null default '',
  category  text not null default '其他',
  grams     numeric(8,1),
  primary key (recipe_id, seq)
);

create table preference (
  household_id text not null references household(id) on delete cascade,
  recipe_id    text not null references recipe(id),
  kind         text not null check (kind in ('like','dislike')),
  source       text not null default '口味档案',   -- 来源痕迹：菜单里点的 / 今晚页 / 做完了打分
  created_at   timestamptz not null default now(),
  primary key (household_id, recipe_id)            -- 互斥：一道菜只在一个列表里
);

create table plan (
  id             text primary key,
  household_id   text not null references household(id),
  week_start     date not null,                    -- 周一
  status         text not null default 'active' check (status in ('active','archived')),
  constraints    jsonb not null,                   -- 需求快照（可复现 R5 的关键）
  profile_sig    text not null default '',         -- 档案签名（缓存键/复现用）
  change_note    text not null default '',
  created_at     timestamptz not null default now()
);
create index plan_current_idx on plan (household_id, status, week_start desc);

create table plan_day (
  plan_id        text not null references plan(id) on delete cascade,
  day_no         int  not null check (day_no between 1 and 7),
  day_date       date not null,
  skipped        boolean not null default false,
  people_override int,                              -- 「来客人了」
  done_at        timestamptz,
  primary key (plan_id, day_no)
);

create table plan_dish (
  plan_id   text not null,
  day_no    int  not null,
  seq       int  not null,
  recipe_id text not null references recipe(id),
  reason    text not null default '',
  locked    boolean not null default false,         -- 「定住」
  primary key (plan_id, day_no, seq),
  foreign key (plan_id, day_no) references plan_day(plan_id, day_no) on delete cascade
);

create table shopping_item (
  id         bigserial primary key,
  plan_id    text not null references plan(id) on delete cascade,
  name       text not null,
  category   text not null,
  amount_text text not null default '',
  grams      numeric(8,1),
  needed     boolean not null default true,
  batch      int check (batch in (1,2)),            -- 分两次买
  optional   boolean not null default false,        -- 单菜小料
  used_for   text[] not null default '{}'
);

create table shopping_check (
  plan_id   text not null references plan(id) on delete cascade,
  item_name text not null,
  checked_at timestamptz not null default now(),
  primary key (plan_id, item_name)
);

create table job (
  id          text primary key,
  plan_id     text references plan(id) on delete set null,
  household_id text not null,
  kind        text not null default 'plan_week',
  status      text not null default 'queued'
              check (status in ('queued','running','succeeded','failed','cancelled')),
  stage       text not null default '',
  progress    numeric(3,2) not null default 0,
  request     jsonb not null,                      -- 需求快照（用于重试）
  error       text,
  created_at  timestamptz not null default now(),
  started_at  timestamptz,
  finished_at timestamptz
);
create index job_active_idx on job (household_id, status, created_at desc);

create table action_log (
  id         bigserial primary key,
  plan_id    text references plan(id) on delete cascade,
  household_id text not null,
  kind       text not null,                        -- swap/like/dislike/lock/skip/people/rate/undo…
  text       text not null,                        -- 给客户看的一句回执（05 §5.3）
  payload    jsonb not null default '{}',          -- 撤销所需快照
  created_at timestamptz not null default now()
);

create table idempotency_key (
  key         text primary key,
  endpoint    text not null,
  status_code int,
  response    jsonb,
  created_at  timestamptz not null default now()
);

create table llm_call_log (
  id          bigserial primary key,
  request_id  text not null default '',
  model       text not null,
  purpose     text not null default 'plan',        -- plan / repair / intent
  prompt_hash text not null,
  tokens_in   int, tokens_out int,
  latency_ms  int,
  ok          boolean not null default true,
  error       text,
  created_at  timestamptz not null default now()
);

create table app_setting (
  key        text primary key,
  value      jsonb not null,
  updated_at timestamptz not null default now()
);
```

### 3.3 关键约束与不变量映射

| 05 的不变量 | 在数据层的保障 |
|---|---|
| R1 单点改动只影响单点 | 所有"改一处"接口只写 `plan_day` / `plan_dish` 的一行，禁止整周重排（重排是独立接口 `POST /plans`） |
| R2 有回执且可撤销 | `action_log.payload` 存撤销快照；`kind+text` 直接用于回执文案 |
| R3 破坏性操作二次确认 | 前端负责二次确认；后端对 `delete` 类接口要求 `confirm=true`，否则 409 |
| R5 结果可复现 | `plan.constraints + plan.profile_sig` 唯一决定菜单；同签名请求命中缓存或复用记录 |
| R6 忌口永不妥协 | `preference(kind='dislike')` 与 `recipe.allergens` 在领域层硬过滤，DB 层加 `check` 兜底 |
| R7 数字带口径 | 金额只存 `cost_yuan`（2 人份基准）与人数，口径在 `reporting` 计算，不落库 |
| R8 状态可见 | `plan_day.skipped / done_at / people_override` + `shopping_check` 就是"我的这一周"的状态源 |

### 3.4 SQLite 与 Postgres 的差异处理

| 特性 | Postgres | SQLite（P0/P1） | 处理 |
|---|---|---|---|
| 数组 | `text[]` + GIN | 不支持 | ORM 用带 `JSON` 类型的 TypeDecorator，读写按 list；过滤在应用层（菜谱 30–150 条，无需 DB 侧检索） |
| JSON | `jsonb` | `JSON` | 同上统一用 SQLAlchemy `JSON` |
| 自增 | `bigserial` | `AUTOINCREMENT` | 用 `BigInteger + Identity`（SQLAlchemy 自动适配） |
| 时间 | `timestamptz` | `TEXT`/ISO | 统一 `DateTime(timezone=True)`；SQLite 下存 UTC ISO |
| 并发写 | MVCC | WAL + 单写者 | P0/P1 打开 `journal_mode=WAL, busy_timeout=5000`；写操作走单会话串行 |
| 全文检索 | `tsvector` | `LIKE` | 菜谱搜索先用 `LIKE`（数据量小），P2 再上 `tsvector` |

### 3.5 迁移与导入

1. **Alembic** 管 schema：`alembic upgrade head` 是唯一的建表方式（禁止 `create_all`）；
2. **一次性导入** `storage/import_json.py`：`recipes.json` → `recipe/ingredient`；`saved_plans.json` → `plan/plan_day/plan_dish/shopping_item/shopping_check`；`customer_profile.json` → `preference/rating`；导入前把三个 JSON **备份到 `data/backup/`**；
3. **等价校验** `scripts/verify_migration.py`：
   - 菜谱：条数、每条的字段逐一比对；
   - 方案：对每个 plan 重新计算 `plan_summary`（花费/天数/命中/最费时），与迁移前 JSON 计算结果比对；
   - 偏好：`liked/disliked/ratings/history` 集合相等；
4. 应用层开关 `STORAGE=json|db`（默认 `db`，出问题一条环境变量回退）。

## 4. Redis（缓存与队列）设计

**Key 规范**（前缀 + 冒号 + 版本，便于整体失效）

| Key | 内容 | TTL | 失效时机 |
|---|---|---|---|
| `rp:v1:recipes:all` | 菜谱库全量（含食材） | 1h | 菜谱库变更 |
| `rp:v1:cands:{sig}` | 检索候选（按约束签名） | 30m | 同上 |
| `rp:v1:plan:{constraints_sig}:{profile_sig}` | **排菜结果** | 7d | 档案/菜谱变更，或用户点"重排一版" |
| `rp:v1:summary:{plan_id}` | 概览/结构/最费时 | 10m | 方案变更 |
| `rp:v1:ratelimit:{scope}:{id}` | 限流计数（令牌桶） | 60s | 自动过期 |
| `rp:v1:job:{job_id}:events` | SSE 事件流（Redis Stream） | 1h | 任务结束 |

**降级**：`REDIS_URL` 未配置或连接失败 → 自动切 `MemoryBackend`（进程内字典 + TTL），只记一条 warning，**接口行为不变**（现有 R5 复现性由签名缓存保证，内存实现同样满足单进程场景）。

## 5. 中间件设计（顺序即执行顺序）

| # | 中间件 | 行为 | 默认参数 |
|---|---|---|---|
| 1 | `RequestIDMiddleware` | 读/生成 `X-Request-ID`，写入 contextvar 与响应头 | 生成 UUID4 |
| 2 | `AccessLogMiddleware` | 结构化 JSON 日志：`ts/level/request_id/method/path/status/latency_ms/household/bytes` | 慢请求 >2s 提升为 warn |
| 3 | `AuthMiddleware` | 家庭级 API Key（`X-API-Key`）；无 key 的部署（本机）自动关闭 | `AUTH_MODE=off|apikey`，默认 `off`（P1），P2 起 `apikey` |
| 4 | `RateLimitMiddleware` | 令牌桶（Redis/内存）：普通接口 60/min，`POST /plans` 6/min（**LLM 贵**） | 超限 429 + `Retry-After` |
| 5 | `IdempotencyMiddleware` | 对 `POST` 且带 `Idempotency-Key` 的请求：命中则返回原响应；执行中返回 409 `in_progress` | 键保留 24h |
| 6 | `SessionMiddleware` | 每请求一个 AsyncSession（Unit of Work），异常回滚、成功提交 | 池 5/10 |
| 7 | `ErrorMiddleware` | 领域异常 → 统一 `problem+json`：`{code,message,request_id,details}`，**`message` 是人话**（05 §5.1 要求失败必须给可点击的下一步，`details.next_steps[]` 直接给前端的放宽选项） | 未捕获异常 500 只记日志不回显堆栈 |
| 8 | `CacheMiddleware` | 只读 GET 支持 `ETag`/`If-None-Match` → 304 | 幂等 GET |

**与 05 §5.1 的对应**：空/加载/失败/成功四类状态的措辞由后端产出（`message` 与 `next_steps`），前端只负责展示与点击 —— 这样"排不出来给可点击的下一步"这条不变量在服务端也成立。

## 6. API 设计

**通用约定**：`/api/v1` 前缀；JSON；时间为 ISO8601 UTC；错误统一 `problem+json`；分页 `limit/cursor`；所有改动类接口返回 `{data, action_log_id, undo_hint}` 以便前端做回执与撤销。

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/health`、`/ready` | 存活 / 就绪（含 DB、Redis、LLM 配置检查） |
| GET | `/api/v1/recipes` | 菜谱库浏览（`q`、`category`、`liked` 过滤）—— 口味档案页用 |
| **POST** | **`/api/v1/plans`** | **排一周**：body = 需求（人数/天数/忌口/预算/厨艺/开始时间…）；需 `Idempotency-Key`；返回 **202** `{job_id}` |
| GET | `/api/v1/plans` | 方案列表（`以前的方案`） |
| GET | `/api/v1/plans/current` | 当前方案（**今晚页**首页数据：今晚菜、时间、金额、理由、几点能吃上、状态①–⑤） |
| GET | `/api/v1/plans/{id}` | 方案详情（7 天 + 每日菜 + 清单 + 概览 + 结构） |
| POST | `/api/v1/plans/{id}/archive` / `/activate` | 切换当前方案 |
| DELETE | `/api/v1/plans/{id}?confirm=true` | 删除方案（无 `confirm` → 409） |
| PATCH | `/api/v1/plans/{id}/days/{day}` | `{op: skip\|restore\|people\|swap\|fastest\|whole_day, ...}` — **单点改动**（R1） |
| POST | `/api/v1/plans/{id}/dishes/{day}/{recipe_id}/feedback` | `{op: like\|dislike\|lock\|unlock}` |
| POST | `/api/v1/plans/{id}/save-money` | 「哪里能省」→ 返回新方案片段 + 省下金额 |
| POST | `/api/v1/plans/{id}/rate` | 「做完了」打分：`{day, score}` |
| GET/PUT | `/api/v1/plans/{id}/shopping/checks` | 勾选进度（幂等 PUT，全量覆盖） |
| GET | `/api/v1/plans/{id}/export/{fmt}` | `csv\|txt\|html`（A4 打印/分享视图）—— 不依赖 UI 也能带走 |
| GET/PUT | `/api/v1/profile` | 档案（喜欢/不喜欢/评分/来源痕迹）+ 批量更新 |
| GET | `/api/v1/profile/export` | 导出档案 JSON |
| POST | `/api/v1/profile/clear?confirm=true` | 清空（二次确认） |
| GET | `/api/v1/jobs/{id}` | 任务状态（兜底轮询） |
| **GET** | **`/api/v1/jobs/{id}/events`** | **SSE 阶段进度**（挑菜→搭配→检查→清单），替代前端轮询 |
| POST | `/api/v1/jobs/{id}/cancel` | 取消（消费端在节点间检查，等价现在的 `PlanJob.cancel`） |

**SSE 事件格式**
```
event: stage
data: {"stage":"plan","label":"正在搭配这一周的菜…","progress":0.45}

event: done
data: {"plan_id":"p_9f2c","week_start":"2026-09-14"}

event: error
data: {"code":"llm_unavailable","message":"这次没排出来，我已经用更保险的排法兜底。",
       "next_steps":[{"op":"relax_time","label":"时长上限放宽到 60 分钟"}]}
```

**任务状态机**：`queued → running(stage,progress) → succeeded | failed | cancelled`；超时（默认 120s）→ `failed(timeout)`；同一 household 的 `plan_week` 任务并发上限 1，多余入队。

## 12. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 过度设计 | 开发时间被基础设施吃掉 | P0/P1 零外部依赖（SQLite + 内存实现）；Redis/Postgres 只在 P2 引入 |
| 迁移丢数据 | 用户资产受损 | 导入前备份 + 等价校验脚本 + `STORAGE` 一键回退 |
| 前端被牵连 | 已验收的界面回退 | 适配层保持同名签名；界面改动集中在"数据源"与"进度来源"两处 |
| R5 被缓存破坏 | 信任问题 | 缓存键 = `constraints_sig + profile_sig`；"重排一版"显式跳过缓存 |
| 单机 SQLite 并发写 | 偶发 `database is locked` | WAL + `busy_timeout` + 写操作串行化（家庭场景足够） |
| 任务重复执行 | 一次生成两版 | 幂等键 + `job` 唯一约束（同 household 单活跃任务） |
