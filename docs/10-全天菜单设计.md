# 10 · 全天菜单（可选餐次）设计

> 编号 **10** ｜ 类型：**设计基线** ｜ 上游：`05`（流程基线）、`06`（样式取值）、`08`（后端架构）、`09`（实现计划）
> 起因：产品负责人的原话是「修改为全天的菜单，然后增加菜品数量」。本文件把这句话变成可实现的约定。
> 结论：**餐次是配置项**（用户勾选吃哪几顿，默认只勾晚餐），不是硬编码的三餐。

---

## 1. 为什么这么做

现在产品是「一周**晚餐**规划」：`models.MEAL = "晚餐"`、`MEALS_PER_DAY = 1`，
`DayPlan` 一天只有一条，`UserConstraints.dishes_per_day` 是"每顿几道菜"。

需求要的是"全天"，但**不能硬编码三餐**：

1. 真实家庭的情况不一样 —— 有人只在家吃早餐、有人只做晚饭、有人三餐都做。
   产品负责人的原话是「根据用户情况实际选择，比如用户可以选择只做早餐或者只做晚餐」。
2. 硬编码三餐会让**不勾早餐的用户**也背上多一顿的复杂度（数据、界面、导出全要变）。
3. 更重要的是：**默认只勾晚餐 = 现有行为一个字都不变**，于是 165（smoke）+ 161/163（self_check）
   + 192（pytest）这三套回归全部继续有效 —— 这是这个设计最大的价值，不是顺带的好处。

## 2. 定下来的取舍（产品负责人已确认）

| 项 | 决定 |
|---|---|
| 餐次 | `早餐 / 午餐 / 晚餐` 三个复选，**默认只勾晚餐**；勾了才排、才进清单 |
| 每餐道数 | 各自一个数，默认 **早 1 / 午 2 / 晚 3**，范围 1–5（原来只有 2 道、上限 4 ——"增加菜品数量"落地在这里） |
| 早餐时长 | **默认 15 分钟**，表单可调 5–30（存进 `breakfast_max_time_min`）；午/晚沿用现有"单菜 ≤ N 分钟" |
| 早餐时长口径 | 粥类按"**≤15 分钟能上桌**"记（用高压锅/预约），**不引入 `hands_on_min` 新字段** —— 多一个字段就要多一套校验与展示，收益不抵成本 |
| 预算 | `budget_per_person_day` 口径**不变 = 每人每天**，覆盖当天勾选的所有餐；表单字段不动，只改提示文案 |
| 默认看哪顿 | 「今晚」页默认看当天勾选的**最后一顿**；只勾晚餐时 = 现在完全一样 |
| 页名 | 只勾晚餐时保持「今晚」；多餐时显示「今天」并在顶部给餐次切换 |
| 早餐菜谱 | 库里 0 道早餐，补 **8 道**（见 §4） |

## 3. 三种做法与选型

**A（采用）：餐次是配置项，`plan_day` 变成"一天一顿"**
- `UserConstraints.meals` 是 `早/午/晚` 的子集，默认 `["晚餐"]`；
- 数据库里 `plan_day`（现在一天一行）改成**一天一行每一顿**，
  `skipped` / `done_at` / `people_override` 自然变成"这一顿"的属性 —— "今天跳过午餐"才说得通。

**B（放弃）：只在 `plan_dish` 上加 `meal` 列，`plan_day` 仍一天一行**
改动小一点，但 `skipped` / `done` / `people` 还是"一天"级 —— "只跳过午餐"表达不了，
界面会出现说不清的状态。**省下的迁移成本，会变成界面上说不清的语义**，不划算。

**C（放弃）：三餐做成三份独立方案**
不动模型，但购物清单要跨方案合并（现在是一份内部合并）、「今晚」页要先选哪一份、
「以前的方案」列表翻三倍 —— 把复杂度推给界面，而且"一天的总花费/总时长"就没人算了。

## 4. 数据模型

### 4.1 常量与约束（`models.py`）

```python
MEALS = ("早餐", "午餐", "晚餐")
MEAL = "晚餐"                      # 保留：老数据/老代码的默认值
MEAL_DISH_DEFAULTS = {"早餐": 1, "午餐": 2, "晚餐": 3}
BREAKFAST_MAX_TIME_DEFAULT = 15    # 早餐时长上限的默认值（实际取 constraints.breakfast_max_time_min）
DISH_MIN, DISH_MAX = 1, 5          # 每餐道数范围（上限从 4 提到 5）
```

### 4.2 `UserConstraints` 的兼容策略（**一处规则，一个地方**）

新增 `meals: list[str] = ["晚餐"]`、`dishes_per_meal: dict[str, int] = {}`，
**保留** `dishes_per_day: int = 2`（老方案、老表单、老接口都在用它）。访问规则只写在方法里：

```python
def active_meals(self) -> list[str]:
    """这一周要排哪几顿，按 早→午→晚 的顺序；空/非法则回落到 ['晚餐']。"""
    picked = [m for m in MEALS if m in set(self.meals or [])]
    return picked or [MEAL]

def dishes_for(self, meal: str) -> int:
    """这一顿几道菜：dishes_per_meal 优先，没写就用 dishes_per_day（老数据兼容）。"""
    return int(self.dishes_per_meal.get(meal) or self.dishes_per_day)

def time_cap_for(self, meal: str) -> int:
    """这一顿单道菜的时长上限：早餐有自己的上限（默认 15 分钟），午/晚用 max_time_min。"""
    if meal == "早餐":
        return int(self.breakfast_max_time_min)
    return int(self.max_time_min)
```

新增字段一览（都带默认值，所以**老数据不用迁移**）：

| 字段 | 默认 | 含义 |
|---|---|---|
| `meals` | `["晚餐"]` | 这一周排哪几顿 |
| `dishes_per_meal` | `{}` | 每餐几道菜；空则回落到 `dishes_per_day` |
| `breakfast_max_time_min` | `15` | 早餐单菜时长上限（ge=5, le=30） |

> 为什么允许两个字段并存：老方案（JSON/DB 里已有 3 份）里只有 `dishes_per_day`。
> 与其写一个数据迁移去猜"晚餐几道"，不如让**读取时**有一条明确的回落规则，
> 且这条规则只出现在 `dishes_for()` 里（`docs/07` §6 第 25 条的教训：两处实现迟早漂）。

### 4.3 `DayPlan`：一天一顿

`DayPlan` 已经在 `models.py` 里有 `meal` 字段（P0 留的口子），现在真正用起来：

- **同一天会出现多条 `DayPlan`**，靠 `(day, meal)` 唯一确定；
- 于是 `next((p for p in result.days if p.day == X))` 这种写法会**静默拿到第一顿** ——
  这是本轮最大的地雷。所有查找必须走 `PlanResult` 上的两个方法：
  ```python
  def slots_for(self, day: int) -> list[DayPlan]:   # 这一天所有餐，按 MEALS 顺序
  def slot(self, day: int, meal: str | None = None) -> DayPlan | None:  # 指定餐；None=最后一顿
  ```
- `DayPlan.skipped` / `people` 的语义收紧为"**这一顿**不做饭 / 这一顿几个人"。

### 4.4 `PlanRecord.done_days` → `done_slots`

"做完了"从"这一天"变成"这一顿"：

- 新增 `done_slots: list[str]`，元素形如 `"3|晚餐"`（`slot_key(day, meal)`）；
- **保留** `done_days: list[int]`：老存档里它表示"当天所有餐都做过了"，
  读的时候由 `record.is_done(day, meal)` 合并判断，写的时候一律只写 `done_slots`。

## 5. 排菜与校验（第②步的落点，先记口径）

- **候选池按餐分**：早餐池 = 分类「早餐」+「主食」+ 蛋类菜品；午/晚池 = 现有的热菜/凉菜/汤/主食。
- **结构规则按餐各跑一遍**：现有"第 1 道偏主菜（含蛋白），第 2 道起补蔬菜/汤"是**按天内的位置**做的
  （`core.py:138-150`），改成按 `(天, 餐)` 各跑一遍即可，规则本身不动。
- **时长**：早餐用 `time_cap_for("早餐")=15`，午/晚用 `max_time_min`。
- **预算**：仍按天汇总（覆盖当天所有餐），超预算的提示口径不变。
- **清单**：本来就是跨天合并的，加餐不增加复杂度；条目上补"用于：午餐、晚餐"。
- **LLM 提示词**：`每天恰好选 N 道菜` → 按餐分别给 N 与"必须是早餐"的约束（`llm_planner.py:78,118`）。

## 6. 界面（第③步的落点）

| 页面 | 改动 |
|---|---|
| 排一周 | 新增「吃哪几顿」三个复选（默认只勾晚餐）+ 每餐道数；早餐的时长上限用 15 分钟 |
| 本周计划 | 每天从"一行"变成"按餐分段"：早餐 1 道、午餐 2 道、晚餐 3 道各一段；上方的整周总览按餐累加 |
| 今晚 | 默认看最后一顿；多餐时页名「今天」+ 顶部餐次切换（只勾晚餐时与现在完全一致） |
| 买菜清单 | 条目上加"用于：午餐、晚餐"；合并与勾选机制不变 |
| 口味档案 | 不变（菜还是那些菜） |

## 7. 接口与数据库（第④步的落点）

- **DTO**：`DayOut` 增加 `meals: list[MealOut]`（每餐的菜/时长/金额/是否做过）；
  `dishes` 保留为"所有餐拍平"，**老客户端不坏**。`ConstraintsOut`/`PlanCreateIn` 增加 `meals` 与 `dishes_per_meal`。
- **数据库**：Alembic `0002` —— `plan_day` 加 `meal VARCHAR`，唯一键改 `(plan_id, day_no, meal)`，
  **已有行填 `'晚餐'`**；`plan_dish` / `shopping_*` 不动（它们挂在 `plan_day` 上）。
- **迁移等价校验**：`scripts/verify_migration.py` 要能覆盖"老库升级后仍是 3 份方案、9 天、18 道菜"。

## 8. 分四步做（每步一个提交 + 一次验证，中间随时能跑）

| 步 | 内容 | 出口标准 |
|---|---|---|
| **①** | 数据模型（`meals` / `dishes_per_meal` / `PlanResult.slot*` / `done_slots`）+ 8 道早餐菜谱 + 「早餐」分类 | **回归零变化**：pytest 192、smoke 165/161、self_check 163/161 全绿（因为默认只勾晚餐，本步是纯增量）；新增模型单测 |
| **②** | 排菜内核：按餐分池、结构规则按餐跑、时长/预算口径、LLM 提示词、清单"用于" | 新增"勾三餐"的内核用例；默认路径回归不变 |
| **③** | 界面：表单勾餐次与每餐道数、本周计划按餐分段、今天页餐次切换 | `smoke_app.py` 仍 165 全绿 + 新增多餐用例 |
| **④** | API/DTO + Alembic `0002` + 导出按餐分段 + 客户端同步 | `verify_migration` 通过；`smoke_api_app.py` 扩展后全绿；真机只读核对 |

## 9. 不做的事（YAGNI）

- **不做 `hands_on_min`（动手时间）**：为了粥类多一个字段，收益不抵成本（§2 已定）。
- **不做"午餐带饭"**：用户要的是可选餐次，带饭是另一种产品形态（多做一份装盒），先不做。
- **不做按餐分预算**：口径保持"每人每天"，需要时再加。
- **不做餐次的排序/自定义名称**：固定早/午/晚三种，顺序固定。
- **不改菜谱库的既有权重**：早餐只加新菜，不动现有 30 道的任何字段。

## 10. 风险与对策

| 风险 | 对策 |
|---|---|
| `p.day == X` 的旧写法静默取到第一顿 | 第①步就把 `PlanResult.slot/slots_for` 建好，并在测试里断言"两条同 day 不同 meal"的查找；第②步逐个改调用点 |
| 老数据（3 份方案）没有 `meals` / `dishes_per_meal` | 读取回落规则只在 `active_meals()` / `dishes_for()` 里；`verify_migration` 覆盖 |
| 早餐池太小（8 道）导致一周重复 | 早餐 1 道 + 8 道池 ≈ 一周不重样；`校验` 里现有的"重复菜"规则会兜住 |
| 一次改动面太大（模型+内核+界面+接口+迁移） | 分四步，每步都能跑、都有独立出口标准（§8） |

## 11. 实施进度

### 第①步 ✅ 数据模型 + 早餐菜谱（2026-09-13）

**做了什么**（全部是纯增量，默认只勾晚餐 → 不勾早餐的用户一个字都不受影响）

- `models.py`：`MEALS` / `MEAL_DISH_DEFAULTS` / `BREAKFAST_MAX_TIME_DEFAULT` / `DISH_MIN,DISH_MAX`；
  `UserConstraints` 增加 `meals`（默认 `["晚餐"]`）、`dishes_per_meal`（默认 `{}`）、
  `breakfast_max_time_min`（默认 15，范围 5–30），并把这三种读取规则**只写在三个方法里**：
  `active_meals()` / `dishes_for(meal)` / `time_cap_for(meal)`。
  老字段 `dishes_per_day` 保留：`dishes_per_meal` 没写时回落到它 —— 这是"老方案不用迁移"的实现方式。
- `PlanResult.slots_for(day)` / `slot(day, meal=None)`：**取 DayPlan 一律走这两个方法**。
  一天多顿之后 `next(p for p in result.days if p.day == X)` 会静默拿到早餐，
  这是本轮最容易犯、最难在界面上看出来的错。
- `PlanRecord.done_slots`（`"3|晚餐"`）+ `is_done(day, meal)`：老存档的 `done_days=[3]`
  当成"那天所有餐都做过了"，同样不做数据迁移。`done_meals_of(day)` 给界面标"已做过"。
- 顺手清掉两处陈旧代码：`MEALS_PER_DAY`（写死 1、已无人引用）、`DayPlan.recipe_ids` 的**重复定义**。
- `core.recipe_conflicts` 增加一条硬过滤：**早餐菜只在勾了早餐时才是候选**。
  没有它，"只做晚餐"的用户会被排出一碗皮蛋瘦肉粥当晚饭 —— 这条也是"回归零变化"的前提。
- `data/recipes.json`：追加 8 道早餐（`r31`–`r38`，全部 ≤15 分钟，分类「早餐」）：
  皮蛋瘦肉粥、小米南瓜粥、番茄鸡蛋面、葱花鸡蛋饼、白煮蛋配黄瓜、燕麦牛奶、吐司煎蛋、香煎速冻饺子。
  按"一行一道菜"的原排版追加，**diff 只多 8 行**（整份重排会让 30 道菜的 diff 全出现，评审时看不出改了什么）。

### 第②步 ✅ 排菜内核按餐分池（2026-09-13）

**做了什么**

- `core.in_meal_pool(r, meal)`：**全项目唯一的**"这道菜属于哪一顿"判定
  （早餐池 = 分类「早餐」+「主食」+ 主料含蛋的菜；其余餐排除早餐菜）。含蛋看**食材名**，不猜菜名。
- `recipe_conflicts(r, c, meal=None)` / `retrieve_candidates(db, c, meal=None)`：给了 `meal` 就按
  那一顿的池子与时长上限判（早餐默认 15 分钟）；**不给 `meal` 时行为与之前完全一致** → 老调用方一行没改。
- `pool_for_meal(candidates, c, meal)`：把 graph 给的候选并集切成"这一顿能用的菜"，复用同一个 `recipe_conflicts`。
- `plan_deterministic`：改成逐天**逐顿**排。每顿用自己的池子与道数；结构规则（第一道偏主菜、
  第二道起补蔬菜/汤）**按餐各跑一遍**（规则本身没改）；**预算仍是"每人每天"，跨餐累加** ——
  不能每顿各花一份预算。
- `validate_plan`：时长上限按餐取；预算**先把当天各餐加起来**（否则"每人每天 ¥45"会被当成"每顿 ¥45"，
  预算校验形同虚设）；文案多顿时带餐次（`第2天早餐`），**单顿时一字不变**（smoke/self_check 上有断言压着）。
- `llm_planner`：多顿时按餐给道数、要求输出 `meal` 字段，缺一顿或道数不对就**整体判不通过**
  （宁可回退到确定性结果，也不留半张全天菜单）；**单顿时提示词与之前一字不差**。

**顺手堵掉一颗地雷**：`core` 里有 **7 处** `next(p for p in plans if p.day == X)`，一天多顿之后它们会
**静默拿到早餐** —— "今晚换一道"会去改早上的粥，界面上完全看不出来（正是 §10 预判的那条）。
新增 `slot_of(plans, day, meal=None)`（None = 当天最后一顿）与 `with_slot()` 之后全部替换；
`skip_day` / `restore_day` / `swap_dish` / `fastest_day` / `pick_replacement` / `candidates_matching` /
`_fits_day_budget` / `replace_in_day` 都加了可选的 `meal` 参数（不传 = 当天最后一顿，单顿时与之前一致）。

**做了什么**

- 「排一周」表单多了一组「**吃哪几顿**」：多选（默认不选 = 只做晚餐），选中哪几顿就出现哪几个
  "N 个菜"控件；勾了多顿时多出"早餐单菜耗时上限"。原来的"每顿几个菜"滑杆**去掉了** ——
  留着就会出现两个互相打架的控件。
- 「本周计划」页：整周总览**每顿一行**（多顿时标出餐次，今天/已过的高亮按**天**算），
  每日详情的标签仍然是**一天一个**（"第 N 天"），页内再按餐分段。
- 「今晚」页：只做晚餐时还叫**今晚**（不能因为加了多餐就改名），多顿时叫**今天**；
  「回家晚了」「来客人了」「这道不吃」都只作用于**当前看的那一顿**。
- 服务端 DTO 补齐 `meals` / `dishes_per_meal` / `breakfast_max_time_min`（`ConstraintsOut` 与 `PlanCreateIn`）
  与 `client._record_from_detail` 的回读 —— 缺了它们，`USE_API=1` 时勾的餐次会被服务端**静默丢掉**。

**两个真 bug（都是这一步自己抓出来的）**

1. **`_dishes_per_meal()` 读错了键**：表单存进 `plan_inputs` 的是 `dishes_per_meal` 字典，
   而它读的是 `dishes_早餐` 这种**扁平键**（那只存在于控件的 session_state 里）→
   每餐道数全部回落成同一个值。用户选"早1/午2/晚3"会得到 3/3/3。**已修**，smoke 现在断言 1/2/3。
2. **数据库模式存不下多餐方案**：`plan_day` 现在是 `PRIMARY KEY(plan_id, day_no)`，
   一天多顿会直接撞唯一约束（`UNIQUE constraint failed`）。这正是第④步那次迁移要解决的，
   所以在迁移做完之前，界面**只在 JSON 存储下开放多餐**（`MEALS_AVAILABLE`）：
   数据库模式下控件是禁用状态并写明原因，绝不会让用户点出一个崩溃。

**⚠️ 一次事故与恢复（记录在案）**：第③步的诊断脚本忘了设 `DATABASE_URL`，
默认走到了**真实库** `data/app.db`，造出 2 版方案（plan 3→5、plan_day 9→18、plan_dish 18→36、
shopping_item 32→59、job 0→2）。发现后按先前核对过的原始状态逐表还原并逐表核对：
**plan 3 / plan_day 9 / plan_dish 18 / shopping_item 32 / shopping_check 0 / preference 1 /
rating 2 / job 0 / action_log 1，当前方案仍是 `b5ea0d22`**，与事故前完全一致。
教训与 `docs/07` §6 的老规矩同源：**临时脚本一律先设 `STORAGE=json` 或把 `DATABASE_URL` 指到 `.tmp/`**。
