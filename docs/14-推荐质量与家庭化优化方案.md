# 14 · 推荐质量与家庭化优化方案

> 编号 **14** ｜ 更新：**2026-09-17** ｜ 状态：**R1-1～R1-3、R2-1～R2-4、R3-S01、C-01、M-01 工具已完成，R1-4 待真实使用数据**
> 上游：`13-最终验收与推进方案.md`（交付收尾）、`12-功能实现对照与改进方案.md`（理想能力对照）
> 默认产品方向：**本地家庭版优先**；服务化稳定作为条件分支，不与本方案的产品能力混做。

---

## 0. 结论先行

项目已经具备“生成菜单 → 调整 → 保存 → 买菜 → 做完反馈”的完整闭环。下一阶段不应继续以页面数量、
菜谱数量或技术名词作为完成度，而应把目标收敛为：

> **在不违反过敏等硬约束的前提下，给出少重复、结构合理、理由可信、能够从真实反馈中逐步改善的家庭菜单。**

本方案的推荐顺序是：

1. 完成 v1 交付收尾，建立可回退的稳定基线；
2. 先修“说得是否诚实”，再优化“排得是否聪明”；
3. 建立产品效果指标，用真实使用数据判断改动是否有效；
4. 增加近期食用惩罚和临时避开语义，解决跨周重复；
5. 把“每顿结构”升级为可验证的策略，而不是继续堆逐菜分数；
6. 有真实家庭使用需求后，再做成员级档案；
7. 外部视频只做小批量人工策展，RAG/MMR/复杂模型延后到数据证明有必要时。

## 1. 目标状态与非目标

### 1.1 下一阶段的理想状态

| 维度 | 理想状态 | 验收信号 |
|---|---|---|
| 安全 | 过敏原等硬约束不可被策略、偏好或放宽逻辑覆盖 | 硬约束违规数始终为 0 |
| 可信 | 推荐理由只描述实际参与选择的因素；营养目标不冒充精确计算 | 理由可由评分明细或结构规则反推 |
| 轮换 | 刚吃过的菜不会因历史喜欢立即重复；长期没吃的菜可适度回归 | 连续两周重合率下降，且不压过明确喜欢 |
| 结构 | 一顿饭按组合验收，而不是每道菜各自“看起来不错” | 所选策略的结构达标率可计算 |
| 学习 | 用户反馈改善后续菜单，但算法自己的展示不被误当成喜欢 | 完成、评分、主动选择与系统曝光分开计权 |
| 家庭 | 多人场景按明确规则合并，冲突可解释 | 过敏取并集、辣度取最严、喜好不伪装成全家共识 |
| 省心 | 菜单、采购和做法形成实际可执行的一周计划 | 换菜次数下降，计划完成率上升 |

### 1.2 本阶段明确不追求

- 不以“用了 RAG / 向量库 / 强化学习”作为先进性的证明；
- 不在营养数据不完整时提供医学或精确营养承诺；
- 不抓取小红书、B 站、抖音内容，不搬运视频或文案；
- 不把本地家庭成员功能扩成账号、云同步或多租户系统；
- 不同时重写推荐算法、服务化链路和界面框架；
- 不为了降低重复率而牺牲过敏、明确不吃、时间上限等硬约束。

## 2. 当前基线与关键判断

### 2.1 已有能力应当保留

- 127 道菜、566 条文字步骤、双存储与完整自动化门禁已经形成稳定基础；
- 偏好事件、时间衰减、吃过记录和轮换奖励已经进入统一排序入口；
- `validate → repair → fallback` 与过敏原兜底是产品安全底座；
- 不同目标和口味已经能让结果发生明显变化，说明现有规则系统不是无效原型。

### 2.2 当前最重要的四个判断

1. **真实反馈样本仍很少。** 当前机制具备学习能力，但不能据此宣称已经理解用户；应先积累
   4–8 周真实使用数据。
2. **轮换只有“久未食用奖励”，缺少“近期食用惩罚”。** 同样输入仍可能每周给出相同菜单。
3. **目标主要由标签驱动。** 当前碳水、脂肪数据不足，减脂/控糖等只能表述为方向性推荐。
4. **家庭画像仍是家庭整体画像。** `AppUser` 只是数据层预留，没有形成成员偏好、参与人和冲突合并闭环。

这些判断决定了下一步应优先做可观测、轮换和结构策略，而不是立即引入向量检索。

## 5. R1：先让推荐“说得可信、效果可测”

### R1-1 推荐理由改为真实因果

当前 `make_reason()` 会在菜品存在任意 `goal_tags` 时给出“营养搭配均衡”，但这并不等于做过营养计算。
本轮已把评分拆成唯一的明细入口 `score_parts(recipe, constraints)`：

```text
score_parts(recipe, constraints) -> [
  {kind: "goal_tag", score: 5.0, text: "符合高蛋白方向"},
  {kind: "taste", score: 1.5, text: "符合清淡口味"},
  {kind: "recent_penalty", score: -3.0, text: "3 天内吃过"},
]
```

- `recipe_score()` 只负责汇总明细；
- `make_reason()` 只从实际生效且分值不为 0 的明细生成文案；
- 结构策略理由来自结构规则，不假装来自单菜评分；
- 没有真实依据时使用“家常、快手、成本友好”等可核对事实；
- 删除泛化的“营养搭配均衡”“滋润暖胃”等无法验证或容易过度承诺的文案；确定性排菜的蛋白/蔬菜/汤结构理由也由结构规则显式传入。
- `recipe_score()` 只汇总明细，`make_reason()` 只消费实际生效分项与菜谱事实；`reason_is_consistent()` 可用于离线验收。
- LLM 只负责选候选菜，返回后的理由由同一套确定性事实重建，避免模型编造因果。

建议涉及：`recipe_planner/core.py`、`recipe_planner/reporting.py`、推荐理由相关测试。

### R1-2 明确营养边界

保留内部值“减脂/控糖/高蛋白”，避免破坏已有数据；只调整用户可见文案：

- “减脂” → “偏清淡/低热量方向”；
- “控糖” → “控糖饮食方向（非营养计算）”；
- “高蛋白” → 数据足够时写“蛋白质较高”，否则写“高蛋白标签方向”；
- 已在生成页和结果页放置简短说明：当前结果基于菜谱标签与已录入营养数据，不等于营养计算或专业建议。

营养字段的使用规则：

- `calories/protein_g/carbs_g/fat_g` 缺失时不得按 0 参与比较；
- 只有覆盖率和数据来源达到约定阈值后，才能将某个数值指标升级为排序因子；
- 结果页的目标统计已改为“标签方向命中”，不再写成“营养达标”。

### R1-3 建立离线产品评估脚本

新增只读脚本，例如 `scripts/evaluate_recommendations.py`，固定输入、固定菜谱库，输出 JSON/Markdown 报告。
至少覆盖：默认、清淡、减脂方向、高蛋白方向、省钱、新手、严格过敏、近期吃过七类场景。

核心指标：

| 指标 | 定义 | 第一阶段目标 |
|---|---|---:|
| 硬约束违规 | 过敏、明确不吃、辣度、餐次、时长冲突数 | **0** |
| 结构达标率 | 满足当前策略的餐次 / 可评估餐次 | R3 前只记录基线 |
| 周内重复 | 同一周重复菜品数 | **0**（候选不足须明确告警） |
| 跨周重合率 | 两周菜品集合的 Jaccard 相似度 | R2 后默认场景建议 ≤ 60% |
| 目标方向命中 | 至少含一道对应标签的餐次比例 | 不低于当前基线 |
| 预算偏差 | 预计总价超过预算的比例与金额 | 不高于当前基线 |
| 解释一致率 | 理由能否由实际评分或策略明细反推 | **100%** |

报告必须保存基线结果，但不要把某次具体数值写死到多个文档中。

本轮新增 `scripts/evaluate_recommendations.py`：固定读取 `data/recipes.json`，覆盖上述八类场景，
输出 `.tmp/recommendation-evaluation/report.json` 与 `report.md`；脚本只读业务数据，不读取或修改本机档案，
并已接入 `scripts/verify.ps1` 的统一门禁。跨周重合率先记录基线，近期食用惩罚留到 R2。

### R1-4 记录真实使用指标

第一版不做仪表盘，只做可导出的周报或本地统计：

- 首次生成后未换菜的餐次比例；
- 每周换菜次数、永久不喜欢次数、临时避开次数；
- 计划完成餐次 / 计划餐次；
- 连续两周重复菜数；
- 做完后“好吃/一般/下次不做”分布；
- 约束被放宽的类型和次数。

这些指标用于比较版本前后变化，不用于给用户打分或制造成就压力。

本轮已新增 `recipe_planner/usage_report.py` 与 `scripts/weekly_usage_report.py`：只读当前本地方案和菜品事件，
输出 Markdown/JSON 周报；默认回看八周，按周合并重复方案，直接接受率只在有完成或换菜证据的餐次中计算。
少于四个观察周时明确写“样本不足”，不输出趋势结论，也不生成模拟用户数据。

**R1 出口**：R1-1～R1-3 已满足——每一句确定性/LLM 展示理由都可追溯；营养边界在界面可见；离线报告可重复生成；固定场景硬约束违规为 0。
R1-4 需要真实家庭使用数据后再记录，不用模拟数据冒充产品效果。

## 6. R2：解决跨周重复和偏好语义混淆

### R2-1 近期食用惩罚

本轮已完成：`rotation_adjustment()` 现在同时表达近期惩罚与长期轮换奖励，区间为 0–2 天 `-3.0`、3–6 天 `-1.5`、7–13 天 `-0.5`、14–29 天 `+0.75`、30 天以上 `+1.5`；从未吃过仍为 `0`。离线评估已用两周固定场景验证跨周重合率，并将候选不足与硬约束问题分开报告。

现有 `rotation_bonus()` 对 14 天内吃过的菜返回 0，只奖励久未食用，没有主动阻止近期重复。建议升级为
单一的 `rotation_adjustment()`：

| 距上次真实食用 | 初始建议分值 | 语义 |
|---:|---:|---|
| 0–2 天 | `-3.0` | 强烈避免立即重复 |
| 3–6 天 | `-1.5` | 一周内适度避开 |
| 7–13 天 | `-0.5` | 轻微降权 |
| 14–29 天 | `+0.75` | 可以轮到 |
| ≥30 天 | `+1.5` | 好久没吃，适度优先 |
| 从未吃过 | `0` | 不伪造偏好，交给其他规则 |

分值必须通过离线场景调参，不能只凭表格直接定版。明确喜欢可以抵消一部分近期惩罚，但默认不得让
“喜欢”变成连续数日重复。候选不足时可以放宽近期惩罚，但必须给出说明，硬约束永不放宽。

### R2-2 分清四种信号

本轮已完成：系统曝光不再产生正向 `SELECT` 权重；主动选择、完成/评分、喜欢/永久不喜欢继续由各自事件或档案语义处理。对应事件权重和回归测试已固定，避免推荐结果通过自我曝光强化。

| 信号 | 含义 | 是否应作为正偏好 |
|---|---|---:|
| 系统排进菜单 | 曝光 | 否 |
| 用户主动保留/换回 | 接受 | 弱正向 |
| 做完或评分 | 实际食用与反馈 | 是 |
| 喜欢/永久不喜欢 | 明确态度 | 强正向/硬排除 |

继续保持“系统生成方案本身不产生吃过事件”。同时复核 `SELECT` 的产生位置，只有用户主动选择时才记录，
避免算法通过自己的输出强化自己。

### R2-3 “这周先别排”与“永久不喜欢”分开

本轮已完成：新增 `snooze` / `unsnooze` 事件与 7 天有效期。菜单页和档案页均可临时避开或恢复，临时避开会尽量只替换当前这一道菜，不写入永久喜欢/不喜欢档案；候选不足时沿用可见的放宽说明。

不需要先改数据库结构。`dish_event.action` 本就允许扩展，可新增：

- `snooze`：本周或未来 7 天临时排除；
- `unsnooze`：提前恢复；
- 永久不喜欢继续使用现有 `dislike` 和档案列表。

检索时的优先级：

```text
过敏等硬约束
  → 永久不喜欢
  → 尚未过期的临时避开
  → 近期食用惩罚
  → 目标、口味、喜欢和轮换加分
```

界面文案必须明确区分“这周先别排”和“不再推荐”。临时避开到期后自然失效，不写入永久档案。

### R2-4 跨周回归测试

本轮已完成：补充近期惩罚、长期奖励、曝光权重、临时避开生命周期、API 撤销、JSON/SQLite 事件适配与固定评估场景回归。当前离线评估的硬约束违规和周内重复均为 0，解释一致率为 100%；真实家庭使用指标仍按 R1-4 积累，不用固定夹具冒充真实效果。

至少增加以下测试：

1. 3 天前做完的菜在候选足够时不进入下一周；
2. 40 天前吃过的菜获得小幅轮换奖励；
3. 明确喜欢不能覆盖永久不喜欢或过敏原；
4. `snooze` 在有效期内排除、到期后恢复；
5. 系统初次生成不产生 `DONE`、`LIKE` 或用户主动 `SELECT`；
6. JSON/SQLite 两种存储的事件语义一致；
7. 候选不足放宽轮换时产生可见说明。

**R2 出口**：默认离线场景跨周重合率达到约定目标；近期菜不会无说明重复；临时与永久偏好行为不同且可恢复。

## 7. R3：从逐菜排序升级为“每顿组合策略”

### R3-1 只做三个预设

S-01 已先落地“日常搭配”这一预设：正餐且至少两道菜时，组合选择优先保证一个蛋白来源和一个非蛋白
蔬菜来源；早餐、单菜餐和候选不足不强行套用。清淡省事、节省食材两个预设仍待后续按同样的指标与放宽
规则独立实现。

第一版不做复杂策略编辑器，只提供三个可解释预设：

| 策略 | 核心规则 | 主要指标 |
|---|---|---|
| 日常搭配 | 正餐且 ≥2 道时，优先包含 1 个蛋白来源 + 1 个蔬菜来源 | 每顿结构达标率 |
| 清淡省事 | 不辣优先、简单优先、组合总操作复杂度较低 | 辣菜比例、较难菜比例、预计耗时 |
| 省钱少浪费 | 预算约束内优先复用主要食材，同时避免连续两道高度相似 | 食材复用率、预计总价、重复度 |

“家有老人”暂不进入第一版，因为现有菜谱缺少软烂程度、咀嚼难度等可靠字段；不能只凭菜名猜测。

### R3-2 数据与接口改动

- `UserConstraints` 新增带默认值的 `strategy`，老数据默认“日常搭配”；
- `constraints` 已按 JSON 存储，SQLite 主表可不因这一字段单独迁移；
- API schema、客户端转换、保存/恢复和界面表单同步增加；
- 预设只表达策略，不复制过敏、辣度、时间等现有字段。

### R3-3 组合评分，而不是继续增加单菜分数

建议增加两个明确入口：

```text
meal_structure_issues(dishes, constraints, strategy)
meal_set_score(dishes, constraints, strategy)
```

- 单菜是否喜欢仍由 `recipe_score()` 负责；
- 蛋白 + 蔬菜、食材复用、组合相似度由 `meal_set_score()` 负责；
- `validate_plan()` 检查策略结果；
- `repair_plan()` 只修不达标餐次，避免整周无谓重排；
- 无法满足时按预先定义的软规则顺序放宽，并把放宽项写入结果。

### R3-4 放宽顺序

统一放宽纪律：

1. 过敏原、永久不喜欢：永不放宽；
2. 辣度、用户明确设置的时间上限：默认不放宽；
3. 临时避开：只有候选不足且用户确认后才放宽；
4. 近期重复、食材复用、结构偏好：可按顺序放宽并说明；
5. 预算超出时显示金额，不用“差不多”掩盖。

### R3-5 验收

- 相同输入切换三个策略后，结构指标按预期变化，而不只是菜名不同；
- 日常搭配的正餐结构达标率达到 90% 以上；不足部分必须来自可证明的候选不足；
- 省钱少浪费的食材复用率高于默认基线，预计总价不升高；
- 清淡省事的辣菜和较难菜比例不高于默认基线；
- 三个策略的硬约束违规均为 0；
- 结果页能解释“本周采用什么策略、哪一餐放宽了什么”。

**R3 出口**：策略差异由结构指标证明；验证与修正链路覆盖策略；用户能看到放宽原因。

## 8. R4：家庭成员档案（有真实需求后启动）

### 8.1 启动条件

满足任一条件再启动：

- 实际连续使用中出现至少两个稳定参与人；
- 因成员口味或过敏冲突，每周需要手工换菜两次以上；
- 用户明确需要按“谁在家吃饭”改变菜单。

### 8.2 第一版范围

只做本地成员，不做登录系统：

- 成员姓名/称呼；
- 过敏原；
- 可接受辣度；
- 永久不吃；
- 喜欢的口味；
- 每周或每餐参与人。

### 8.3 合并规则

| 类型 | 合并方式 |
|---|---|
| 过敏原 | 参与成员并集，硬约束 |
| 辣度 | 取最严格值 |
| 永久不吃 | 任一参与成员否决即排除；界面说明是谁的约束 |
| 喜欢 | 按参与成员投票或平均，不允许单人喜好冒充全家喜好 |
| 目标 | 仍是本周家庭目标，不从个人健康信息自动推断 |
| 份量 | 按参与人数和已有份量逻辑计算 |

### 8.4 数据建议

复用已有 `household` / `app_user`，新增成员约束关联；`dish_event` 增加可空 `user_id` 时必须提供迁移和
老数据回落规则：旧事件归属家庭，不强行猜测成员。JSON 后端必须保留同等语义。

### 8.5 验收

- 老用户不创建成员时行为完全不变；
- 选择不同参与成员能改变候选池和解释；
- 任一成员过敏原都不会被违反；
- 冲突时显示“因为某成员不吃/过敏而排除”，不暴露多余隐私；
- 成员删除或改名不破坏历史方案。

## 9. R5：外部视频与内容策展

### 9.1 策略

保留现有“直链优先、搜索兜底”，先为 10–20 道高频或易翻车菜人工选择视频，不追求一次覆盖 100 道。

优先级：

1. 使用频率高；
2. 步骤文字难表达火候或状态；
3. 用户反馈容易翻车；
4. 视频来源稳定、标题与菜品匹配。

### 9.2 最小元数据

后续可在 `video_url` 之外增加：平台、标题、作者、人工复核日期。只保存链接与必要描述，不下载、不转录、
不抓取平台内容。平台链接不可用时继续展示搜索入口，不让做法功能整体失效。

### 9.3 验收

- 每个直链都由人工打开确认；
- 链接对应正确菜品，不以搜索结果第一页自动填充；
- 失效后可回落到搜索入口；
- 界面明确“参考视频来自外部平台”；
- 文字步骤始终保留，视频不是唯一做法来源。

## 10. 服务化条件分支

在 R0 前做一次范围决定：

### 如果目标是本机家庭使用

- `USE_API=1` 维持可测试的实验能力；
- 不为了架构完整优先投入多租户、Redis、Postgres 或云部署；
- 先完成 R1–R3，以实际使用价值为主。

### 如果目标包含正式服务部署

必须先执行 `13` 的 B 阶段：SSE 终态回查、缓存隔离、任务 reaper、幂等键生命周期、可信身份分桶、
拆除 `update_result` 过渡桥。完成前不得把 API 模式描述为生产稳定。

服务化与 R1/R2 可以分提交并行设计，但不能在同一次变更中同时重写任务链路和推荐核心。

## 11. 暂缓项的恢复条件

| 暂缓项 | 何时重新评估 |
|---|---|
| 偏好 RAG / 向量库 | 菜谱进入大规模非结构化内容，且标签检索的漏召回有可复现实例 |
| MMR | R2 完成后跨周重合率仍高，且问题来自组合相似而非近期食用规则 |
| 精确营养优化 | 核心营养字段覆盖率和来源质量达到产品声明要求 |
| 自适应衰减 | 单菜事件量足以分训练/验证，手工常数出现稳定偏差 |
| 强化学习/序列模型 | 有足够多用户和反馈，不再是单家庭小样本 |
| “家有老人”预设 | 菜谱具备软烂、咀嚼难度等可信字段 |
| 账号/云同步/多租户 | 出现跨设备或第二独立家庭的真实使用需求 |

恢复任何暂缓项时，都要先写清：当前规则哪里失败、失败频率、现有数据能否验证新方案、失败后如何回退。

## 12. 推荐执行节奏

### 第 1 周：封板与可信度

- 完成 R0；
- 落地评分明细与可信理由；
- 增加营养边界说明；
- 建立离线评估报告并保存基线。

### 第 2 周：轮换和偏好语义

- 增加近期食用惩罚；
- 复核 `SELECT` 事件来源；
- 增加“这周先别排”；
- 用固定场景比较跨周重合率和目标命中率。

### 第 3 周：结构策略

- 先实现“日常搭配”；
- 通过后再加“清淡省事”和“省钱少浪费”；
- 每增加一个策略，都必须同时增加指标、放宽规则和测试。

### 第 4～8 周：真实使用观察

- 每周实际排菜、调整、完成和评分；
- 只记录指标，不在中途频繁改权重；
- 第 4 周做一次小复盘，第 8 周决定是否启动 R4/R5 或 MMR；
- 没有数据支持的功能继续保持 `HOLD`。

## 13. 总体验收标准

本方案不以“全部功能都做了”为完成，而以以下结果为完成：

1. 自动化门禁继续全绿，硬约束违规数为 0；
2. 推荐理由 100% 可由实际评分项、菜谱事实或结构策略反推；
3. 默认场景连续两周重合率达到约定目标，近期吃过的菜不会无说明重复；
4. 临时避开与永久不喜欢有不同生命周期，用户能够撤回；
5. 至少一个结构策略达到 90% 以上的可评估餐次达标率；
6. 真实使用 4–8 周后，换菜次数没有上升，计划完成率没有下降；
7. 若启动家庭成员功能，任何参与成员的过敏约束均不得违反；
8. RAG、MMR 或复杂模型只有在规则失败证据存在时才进入实现。

最终希望形成的产品不是“技术最复杂的菜单生成器”，而是一个用户敢相信、愿意持续反馈、每周确实能
少操心一点的家庭饮食决策工具。
